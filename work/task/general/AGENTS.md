# 任務規劃規範

## 1. 來源與路徑

1. 啟動 task 流程時，先確認使用者目前輸入或規格交接是否已明列需求編號；已明列且格式有效時直接使用並不得重問，未明列時才請使用者輸入。不得從其他對話內容、檔名、路徑或目前目錄推測；需求編號只能使用小寫英數、`.`、`_`、`-`，且不得為 Windows 保留名稱。
2. 驗證需求編號後，預設讀取 `outputs/plans/<requirement-id>.md`，並將 TASK 寫入 `outputs/tasks/<requirement-id>.md`、將 execution 寫入 `outputs/executions/<requirement-id>/`。
3. 使用者明確指定並確認其他專案相對路徑時才可覆寫預設路徑，且 Plan、TASK 與 execution 的需求編號及對應必須一致。
4. 正式 TASK 只能由同需求編號的已確認 Plan 產生；一份 Plan 對應一份持續維護的 TASK 文件。
5. TASK 必須自足，不保存可由需求編號推導的來源路徑、Plan 狀態或同步基準。
6. 建立正式 TASK 前，先讀取已確認 Plan、完成必要的唯讀探索，並逐項詢問所有會影響成果、範圍、檔案、步驟、命令、外部操作或驗證的問題；每項回答均須獲得確認，且不得留有未決問題。
7. 未完成全部確認時，草案只在對話中提供，不得建立 TASK、execution index、Attempt、檔案或相關目錄；全部問題確認後，先提供完整 TASK 草案，經使用者明確核准才在同一已授權最小任務中建立正式 TASK 與初始 index。
8. 讀取、建立或移動 Plan、TASK、execution index 或 execution 目錄前，須以平台實際路徑規則正規化全部對應路徑：預設路徑須分別保留在專案根目錄下的 `outputs/plans/`、`outputs/tasks/` 及 `outputs/executions/` 邊界內，其他路徑須保留在專案根目錄內；不得接受絕對路徑或空路徑，移除單一開頭的 `./` 或 `.\` 後不得含 `.`／`..` 路徑片段，也不得接受正規化後改變需求編號對應片段、三者互相別名或與不同字面名稱產生平台別名衝突的路徑。既有路徑及最接近的既有祖先若包含 symlink／junction，須解析實際目標並確認仍在適用邊界內；任一項無法確認時停止並維持對話草案。

## 2. 規格基準

1. TASK 不保存規格狀態；對話草案使用 `TASK-SPEC-DRAFT`，且不建立 SHA、execution index 或變更紀錄。
2. 正式初版使用 `TASK-SPEC-001`，並與初始 index 在同一已授權最小任務中建立；全部 TASK 初始為「待執行」，不建立 Attempt。
3. TASK 只保存 `TASK-SPEC-*`，SHA-256 保存於 index；TASK SHA-256 演算法固定為：以 UTF-8 嚴格解碼 TASK 位元組，移除僅位於文字開頭的 U+FEFF BOM，依序將全文正規化為 Unicode NFC、將 CRLF 與其餘 CR 轉為 LF、移除檔尾全部 LF 後補回單一 LF，再以 UTF-8 無 BOM 編碼並對所得位元組計算 SHA-256；index 的 `TASK-SHA-256` 固定保存 64 個小寫十六進位字元。
4. BOM、CRLF／LF／CR 差異及純需求編號重新命名不升版，其他正規化後文字變更皆升一版；一次核准可新增多筆 `TASK-CHANGE-*`，但 `TASK-SPEC` 只升一版。
5. Execute 不得修改 TASK。

## 3. 維護與鎖定

1. 修改規格前須先依 execute 規則結案所有進行中的 Attempt，並確認 index 沒有執行鎖；執行鎖存在時只能交由 execute 流程依其恢復規則處理，plan／task 流程不得自行解除。
2. 只影響檔案、命令或驗證等執行細節時，只更新 TASK 與 index；影響 Plan 目標、範圍、成果、驗收或決策時，同步更新 Plan、TASK 與 index。
3. 修改 TASK、execution 路徑或兩者對應前，先確認 index 沒有執行鎖，再寫入 `規格鎖：更新中`；規格鎖與執行鎖不得同時存在。中斷時保留規格鎖，且只能由 plan／task 流程在重新確認現況、取得授權並完成全部寫入與一致性檢查後解除。
4. 純需求編號重新命名不升版；先確認新路徑不存在，再於鎖定下移動 Plan、TASK 與 execution 並驗證對應。所有多檔更新均屬同一邏輯原子最小任務，任一寫入或檢查失敗即停止並回報現況。
5. 已完成 TASK 因新規格需要追加工作時，不修改或重開原 TASK；建立下一個 `TASK-ID`。
6. 規格變更時，受影響的已完成 TASK 及其所有已完成下游改為「待重新執行」；既有 Attempt 僅供稽核，未受影響 TASK 的證據即使記錄舊版 TASK-SPEC 或 SHA 仍有效，影響範圍以 `TASK-CHANGE-*` 的受影響 ID 為準。
7. 規格變更確實解除最新有效 Attempt 所記錄的規格缺陷，且沒有其他仍成立的阻礙時，將對應的「受阻」TASK 改為「待重新執行」，並在 index 以本次 `TASK-CHANGE-*` 記錄狀態差異原因；外部服務、環境、權限、必要輸入或其他阻礙仍成立時維持「受阻」。
8. 只有 plan／task 流程能在已核准規格變更中取消 TASK；「進行中」TASK 必須先依 execute 規則結案並解除執行鎖，其他狀態均可取消。取消時保留原 TASK 定義與全部 Attempt／Correction，新增 `TASK-CHANGE-*` 記錄原因及受影響 ID，並將 index 狀態設為「已取消」。
9. 取消 TASK 前須逐項列出所有直接及間接受影響的下游 TASK；仍需要的下游須在同一規格變更中移除或改寫相依與輸入，不再需要的下游一併取消。規格更新完成後，不得有未取消 TASK 保留指向已取消 TASK 的有效相依。
10. 已取消 TASK 不得重新啟用、修改或重開；需求恢復時使用下一個新 `TASK-ID` 重新規劃相依與驗證。既有 TASK 文件新增的任何 TASK，包括已取消 TASK 的替代項目，均以「待執行」加入 index。

## 4. 識別碼與變更

1. 初版 TASK 依相依順序編號，後續新增只取下一號；所有識別碼建立後不得重新編號或重用。
2. 執行順序只依明確相依關係，不依 TASK 編號。
3. 影響至少兩個 TASK 的共用決策使用文件層 `DECISION-*`，依 ID 順序固定放在文件層欄位之後、第一個 TASK 之前，格式為 `DECISION-001：<已確認決策>`；其他決策留在個別 TASK 的「決策」清單。每個 TASK 的 `CMD-*`、`OP-*` 及 `VAL-*` 分別由 `001` 起編號。
4. `TASK-CHANGE-*` 由 `TASK-CHANGE-001` 起遞增，只記日期、適用時的 `PLAN-CHANGE-*`、位置、`前 → 後`、原因及受影響 ID；相同原因與同一成果合併一筆，不保存執行狀態或證據。

## 5. TASK 內容

1. 每個 TASK 使用固定二級標題 `## TASK-001：<名稱>`，下一個二級標題為區段終點；必要內容為一行追溯 ID、一句單一成果目標、精簡編號步驟及至少一個 `VAL-*`。
2. TASK 內欄位只使用下列名稱及順序：`追溯`、`相依`、`輸入`、`決策`、`目標`、`檔案`、`風險`、`步驟`、`CMD-*`、`OP-*`、`VAL-*`。必要欄位不得省略；選用欄位沒有內容時整段省略，不寫「無」或「不適用」，其餘欄位不得改名、重排或加入同義欄位；同類 ID 依數字遞增排列。
3. `追溯` 只列適用的 `GOAL-*`、`DELIVERABLE-*`、`ACCEPTANCE-*` 及選用的 `MILESTONE-*`，以 `、` 分隔；`相依` 只列直接相依的 `TASK-*`，以 `、` 分隔。引用前序產物時必須建立相依，並在 `輸入` 編號清單逐項使用 `來源：<檔案、類別、測試或其他產物>；執行前條件：<必須仍成立的可觀察條件>`。
4. `決策` 使用編號清單；共用決策項目只列既有 `DECISION-*`，TASK 專屬項目直接記錄已確認方案。適用的下層規則要求 TASK 固定或明列，但沒有其他既有欄位專門承載的架構、契約、責任邊界、技術事實或例外，只影響一個 TASK 時記為該 TASK 的專屬 `決策` 項目，影響至少兩個 TASK 時建立文件層 `DECISION-*` 並由各 TASK 引用；不得為此新增欄位或同義欄位。`風險` 使用編號清單，逐項固定為 `條件：<風險條件>；影響：<影響>；處置：<已確認處置>`。
5. TASK 不得保留未決的候選執行方案；已確認的產品條件行為不在此限。執行方案無法固定時維持草案，先唯讀確認或逐項詢問，不得核准。
6. 正式 TASK 的文件層必須記錄 `規則層級`，值為 task 流程正規化後的完整選取層級名稱，依載入順序以 ` → ` 分隔並包含開頭的 `general`；只記名稱，不記使用者層級或專案層級規則檔案路徑及雜湊。規則層級變更視為 TASK 內容變更，須依第 2、3 節升版並同步 index。

## 6. 檔案與步驟

1. `檔案`只列完成 TASK 必須成立的變更，使用編號清單並依 `建立`、`修改`、`移動` 分組排序；每項固定為 `建立：<path>`、`修改：<path>` 或 `移動：<來源> → <目的>`，不規劃由 AI 刪除檔案。
2. 已核准命令正常產生且不屬交付成果的 `target/`、`build/`、測試報告等暫存輸出不列入檔案。
3. 步驟只描述必要順序、編輯內容及引用的 `CMD/OP/VAL`，不建立步驟 ID 或重複其他欄位全文。

## 7. CMD、OP 與 VAL

1. `CMD-*` 保存精確命令，短命令用行內程式碼，多行命令用程式碼區塊；有 CMD 時，文件層只記一次預設工作目錄與 `執行環境：OS／shell`，個別命令僅在不同時覆蓋。
2. 文件路徑使用專案相對路徑與 `/`；命令只提供已確認環境適用的一種 shell 寫法。
3. `OP-*` 只用於外部狀態操作，每項固定為 `OP-001：操作：<操作>；目標：<目標>；驗證：<VAL-ID>`；沒有 OP 時整段省略。
4. 每個 `VAL-*` 只保存驗證類型、執行方式及客觀通過條件，並在正式 TASK 核准前依下列規則固定，不得交由 execute 臨時選擇或替換工具：
    1. 內容、結構、路徑、編碼、Unicode、編譯、測試數量或其他可用確定性斷言客觀判定的條件，必須規劃為自動驗證，固定格式為 `VAL-001：自動；執行：<CMD-ID 清單>；通過：<客觀條件>`；引用多個 CMD 時以 `、` 分隔。所有 CMD 必須由 TASK 明列並依第 8 節完成預檢；不得以人工檢視取代可自動化的精確檢查。
    2. 人工 VAL 只用於無法穩定自動判定且確實需要判斷的結果，固定格式為 `VAL-001：人工；確認者：<確認者>；判準：<可觀察判準>`，不得只寫「人工確認正常」。
    3. 尚未確定可靠的自動驗證命令、人工確認者或可觀察判準時，維持對話草案，不得建立正式 TASK。
5. 只有直接驗收成果的 VAL 才在固定格式末尾加入 `；驗收：<ACCEPTANCE-ID 清單>`，多個 ID 以 `、` 分隔；每個 `ACCEPTANCE-*` 必須至少由一個最終 VAL 覆蓋。

## 8. 規劃檢查

1. 規劃流程可直接執行必要的唯讀探索，不建立探索 TASK 或 Attempt；具副作用的預檢須先取得授權，失敗只在對話回報並停止，不建立 execution 紀錄。
2. 核准前須在不執行具副作用命令本體的前提下，以目標 shell 解析每個 `CMD-*` 的語法；對規劃時已可用的本機命令入口、模組及執行階段型別另做唯讀解析檢查，不得只因語法解析成功就判定命令可用。
3. 核准前確認相依關係無自我或循環相依，且輸入、檔案操作、命令、外部操作、VAL 及驗收覆蓋完整且無候選方案。
4. 請求使用者核准完整 TASK 草案前，須先在同一對話回覆提供就緒檢查證據摘要，至少逐項列出：
    1. 實際載入的 task 規則檔案與層級順序。
    2. 專案架構、路徑、套件、命名、引用符號及其他適用唯讀探索的最小證據。
    3. 相依、輸入、檔案操作，以及每個 Red 的測試來源、編譯骨架與步驟順序檢查結果。
    4. 每個 `CMD-*` 的目標 shell 語法、命令入口、模組與執行階段型別預檢結果。
    5. 每個 `VAL-*` 的自動／人工分類、執行方式、客觀通過條件及 `ACCEPTANCE-*` 覆蓋結果。
5. 證據摘要的每個適用項目須記錄可核對的通過證據；未通過、無法確認或不適用時，分別記錄具體原因，不得只寫「已檢查」或「符合規範」。
6. 任一適用項目未通過或無法確認時，維持對話草案，只列缺漏並繼續釐清，不得請求正式核准、建立 TASK 或寫入就緒結論。
7. 全部適用項目均有通過證據後，才可請求使用者核准完整 TASK 草案；正式文件結尾仍只記 `就緒檢查：已通過 <TASK-SPEC-ID> 適用規範`，不將證據摘要寫入 TASK。

## 9. 最小骨架

```markdown
# <任務文件名稱>

TASK-SPEC：TASK-SPEC-001
規則層級：general
預設工作目錄：<相對路徑>
執行環境：<OS／shell>
DECISION-001：<已確認決策>

## TASK-001：<名稱>

追溯：GOAL-001、DELIVERABLE-001、ACCEPTANCE-001
相依：<TASK-ID>
輸入：
1. 來源：<前序產物>；執行前條件：<可觀察條件>
決策：
1. DECISION-001
目標：<單一成果>
檔案：
1. 修改：<path>
風險：
1. 條件：<風險條件>；影響：<影響>；處置：<已確認處置>
步驟：
1. <步驟及引用 ID>
CMD-001：`<命令>`
OP-001：操作：<外部操作>；目標：<目標>；驗證：VAL-002
VAL-001：自動；執行：CMD-001；通過：<客觀條件>；驗收：ACCEPTANCE-001
VAL-002：人工；確認者：<確認者>；判準：<可觀察判準>

就緒檢查：已通過 TASK-SPEC-001 適用規範
```

### 初始 execution index

```markdown
# Execution

TASK-SPEC：TASK-SPEC-001
TASK-SHA-256：<sha>
整體狀態：待執行

TASK-001：待執行
```

1. 每個 TASK 依文件順序各列一行「待執行」；初始 index 不建立 Attempt、Correction、阻礙、狀態差異原因、規格鎖或執行鎖。
2. 沒有內容的選用欄位與章節直接省略。
