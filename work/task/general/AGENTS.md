# 任務規劃規範

## 1. 適用範圍

1. 本規範用於將已確認的計畫拆解成可由 AI 穩定執行、客觀驗證及持續追蹤的最小任務。
2. 來源計畫統一為專案根目錄的 `./plans/<plan-name>.md`。
3. 任務文件統一為專案根目錄的 `./tasks/<plan-name>.md`。
4. 一個計畫只能對應一個同名任務文件。
5. 任務文件應跟隨來源計畫使用的主要語言；使用者另有指定時，以使用者指定為準。
6. 本規範負責建立及維護任務文件，不得直接執行任務內容。

## 2. 來源計畫檢查

1. 產生或維護任務文件前，必須完整讀取 `./plans/<plan-name>.md`。
2. 只有整體狀態為「已確認」的計畫可以產生任務文件。
3. 下列任一情況發生時，必須停止並回報使用者：
   1. 使用者未指定來源計畫。
   2. 來源計畫不存在。
   3. 來源計畫無法完整解析。
   4. 來源計畫狀態不是「已確認」。
   5. 來源計畫缺少任務拆解所需的識別碼或必要內容。
4. 不得以對話內容、推測或其他文件取代來源計畫中的正式內容。
5. 若來源計畫與使用者的新指示衝突，必須指出衝突，並先由適用的計畫規範處理計畫變更。

## 3. 職責邊界

1. 任務規劃負責定義：
   1. 每個任務要產生的單一成果。
   2. 任務與計畫項目的追溯關係。
   3. 任務的前置條件與相依關係。
   4. 預計修改的精確檔案。
   5. 可重複執行的具體步驟與命令。
   6. 預期輸出、驗證方式及通過條件。
   7. 限制與已知風險。
2. 任務規劃不得：
   1. 改寫來源計畫的目標、範圍、交付成果、驗收標準或里程碑。
   2. 自行補充來源計畫未確認的需求。
   3. 將多個可分離成果合併成一個任務。
   4. 直接執行、提交或宣稱完成任務。

## 4. 需求釐清

1. 產生任務文件前，必須確認每個任務的目標、範圍、限制、輸出及驗證方式均已明確。
2. 必須先以唯讀方式檢查專案架構、既有慣例、可用命令及相關檔案，再判斷資訊是否充足。
3. 無法從來源計畫與專案現況確定必要資訊時，必須逐題詢問使用者。
4. 每次只能提出一個問題。
5. 每個問題必須提供明確且有編號的選項，並標示建議選項及簡短理由。
6. 收到回答後，必須更新並重述目前已確認的需求。
7. 禁止留下「執行時決定」、「視情況」、「適當處理」或其他要求執行 AI 自行推測的內容。
8. 尚有會影響任務成果、檔案、步驟、命令或驗證的待確認事項時，只能在對話中提供草案，不得寫入任務文件。

## 5. 拆解原則

1. 每個任務必須產生一個單一、明確且可獨立驗證的成果。
2. 任務應拆到在一次取得授權後，可以不中途改變範圍地完成及驗證。
3. 完成單一成果所必需且不可分割的檔案修改與驗證，可以包含在同一任務。
4. 符合下列任一條件時，應拆成不同任務：
   1. 可以獨立產出或驗收。
   2. 需要不同的執行授權。
   3. 具有不同的前置條件。
   4. 失敗後可以獨立回復或重新執行。
   5. 涉及不同且可分離的外部狀態變更。
5. 不得為了減少任務數量而犧牲可執行性、可驗證性或結果一致性。
6. 任務步驟必須採用固定順序，避免同一任務存在多條未指定選擇條件的實作路徑。
7. 相同的初始狀態、輸入與工具版本下，依任務規格執行應產生相同的預期結果。

## 6. 排序與分章

1. 任務文件必須依來源計畫的 `MILESTONE-*` 順序分章。
2. 每個任務必須歸入最早需要執行該任務的里程碑章節。
3. 任務不必與里程碑一對一；一個里程碑可包含多個任務。
4. 任務若支援多個里程碑，必須列出全部對應里程碑，但只在最早的對應里程碑章節出現一次。
5. 每個里程碑章節內，任務必須依相依關係及實際執行順序排列。
6. 可平行執行的任務必須明確標示，不得僅由排列位置暗示。
7. 不得建立循環相依。

## 7. 穩定識別碼

1. 每個任務必須配置唯一且穩定的識別碼，格式為 `TASK-001`。
2. 識別碼使用三位數流水號，並依整份任務文件的執行順序配置。
3. 識別碼建立後不得因重新命名、重新排序或移至其他里程碑而變更。
4. 刪除任務後，其識別碼永久保留，不得重新使用。
5. 新任務必須使用下一個未使用的流水號。
6. 相依關係、變更紀錄與執行回報均必須使用任務識別碼。

## 8. 追溯關係

1. 每個任務必須列出所有直接相關的來源計畫識別碼。
2. 追溯關係至少必須包含：
   1. 對應里程碑：`MILESTONE-*`。
   2. 對應交付成果：`DELIVERABLE-*`。
   3. 對應驗收標準：`ACCEPTANCE-*`。
3. 適用時，應另外列出對應目標 `GOAL-*` 及成功條件 `SUCCESS-*`。
4. 不得建立來源計畫中不存在的識別碼。
5. 每個交付成果及其驗收標準都必須至少由一個任務涵蓋。
6. 若無法建立完整追溯關係，必須停止並請使用者先修正或確認來源計畫。

## 9. 任務必要格式

1. 每個 `TASK-*` 必須使用獨立的固定欄位區塊。
2. 每個任務必須包含：
   1. 任務名稱。
   2. 狀態。
   3. 任務目標。
   4. 對應里程碑。
   5. 對應交付成果。
   6. 對應驗收標準。
   7. 適用的其他計畫識別碼。
   8. 前置條件。
   9. 相依任務。
   10. 可平行任務。
   11. 預計修改的檔案。
   12. 輸入與初始狀態。
   13. 執行步驟。
   14. 預計執行的命令或外部操作。
   15. 預期輸出。
   16. 驗證方式。
   17. 通過條件。
   18. 限制。
   19. 已知風險。
3. 不適用的欄位必須保留並寫明「不適用」及原因。
4. 檔案路徑必須相對於專案根目錄，並精確到檔案；不得只列目錄或未解析的萬用字元。
5. 新增檔案必須明確標示「新增」；修改既有檔案必須標示「修改」。
6. 命令必須包含執行目錄、完整命令及必要參數。
7. 外部操作必須列出目標系統、操作內容及可觀察結果。
8. 驗證方式必須是實際可執行的命令或明確人工檢查程序。
9. 通過條件必須客觀且可判定，不得只使用「正常」、「完整」或「沒有問題」。
10. 若任務包含具副作用的驗證，必須將該操作明列於命令或外部操作中。

## 10. 任務狀態

1. 任務只能使用下列狀態：
   1. 待執行：規格已確認但尚未開始。
   2. 進行中：已取得執行授權並開始執行。
   3. 受阻：存在明確阻礙，無法繼續。
   4. 已完成：所有步驟完成且通過條件已有實際證據。
2. 初次產生任務文件時，所有任務狀態均為「待執行」。
3. 任務狀態變更前必須取得使用者確認。
4. 標記為「受阻」時，必須記錄阻礙原因及解除條件。
5. 標記為「已完成」時，必須記錄實際執行的驗證及結果。
6. 未實際取得驗證證據時，不得將任務標記為「已完成」。

## 11. 任務文件基本資訊

1. 任務文件開頭必須使用 Markdown 資訊表。
2. 資訊表至少包含：

| 欄位 | 說明 |
|---|---|
| 任務文件名稱 | 與來源計畫名稱一致 |
| 狀態 | 使用本規範定義的整體文件狀態 |
| 來源計畫 | `./plans/<plan-name>.md` |
| 來源計畫狀態 | 必須為「已確認」 |
| 建立日期 | 使用 `YYYY-MM-DD` |
| 最後更新日期 | 使用 `YYYY-MM-DD` |

3. 任務文件只能使用下列整體狀態：
   1. 草案：內容仍在釐清或等待整份核准。
   2. 已確認：使用者已明確核准整份任務文件。
   3. 進行中：至少一個任務已開始，且文件尚未完成。
   4. 受阻：重大阻礙使整份任務文件無法繼續。
   5. 已完成：所有必要任務均已完成，且來源計畫對應驗收均有證據。
   6. 已取代：已有另一份任務文件正式取代本文件。
4. AI 不得自行將文件從「草案」改為「已確認」。
5. 任何整體狀態變更都必須先取得使用者確認。
6. 標記為「受阻」時，必須說明阻礙及解除條件。
7. 標記為「已取代」時，必須指出取代本文件的新文件。

## 12. 草案與寫入流程

1. AI 必須先在對話中提供完整任務文件草案。
2. 草案必須標示為「草案」，且所有任務初始狀態為「待執行」。
3. 使用者核准前，不得建立或修改 `./tasks/<plan-name>.md`。
4. 使用者明確核准整份草案後，才能：
   1. 將文件狀態改為「已確認」。
   2. 提出寫入任務文件的最小任務。
5. 寫入檔案前仍須取得使用者明確執行授權。
6. 任務文件獲得核准不等於其中任何任務已獲執行授權。
7. 執行 AI 每次只能提出並執行一個最小任務，且每次均須另行取得使用者確認。

## 13. 既有任務文件維護

1. 若 `./tasks/<plan-name>.md` 已存在，必須視為既有文件維護，不得重新產生或覆寫。
2. 維護前必須比較：
   1. 目前已確認的來源計畫。
   2. 來源計畫變更紀錄。
   3. 既有任務正文、識別碼及狀態。
   4. 既有任務變更紀錄。
3. 必須保留既有 `TASK-*` 識別碼、執行狀態、驗證結果及變更歷史。
4. 已完成任務受計畫變更影響時，不得直接改回其他狀態；必須提出新增任務或狀態調整草案供使用者確認。
5. 所有語意變更都必須先在對話中提供草案，經使用者核准及另行授權後才能寫入。
6. 純排版或不影響語意的錯字修正可以直接更新正文，但仍須遵守檔案修改授權規則。

## 14. 變更紀錄

1. 修改任務內容時，必須直接更新原章節，使正文代表目前有效版本。
2. 變更紀錄分為：
   1. 來源計畫衍生變更。
   2. 任務文件獨立變更。
3. 來源計畫衍生變更編號格式為 `<PLAN-CHANGE-ID>-TASK-<n>`。
4. 例如來源計畫的 `CHANGE-003` 造成兩筆任務變更時，依序使用 `CHANGE-003-TASK-1` 與 `CHANGE-003-TASK-2`。
5. 同一來源計畫變更的 `<n>` 從 `1` 開始依序遞增，不得重複使用。
6. 任務文件獨立變更編號格式為 `TASK-CHANGE-001`，使用三位數流水號。
7. 已使用的變更編號不得修改或重複使用。
8. 每筆語意變更必須記錄：
   1. 變更編號。
   2. 日期。
   3. 來源 plan 變更。
   4. 原文位置。
   5. 修改前內容。
   6. 修改後內容。
   7. 修改原因。
   8. 受影響項目。
9. 來源計畫衍生變更的「來源 plan 變更」必須填入對應的 `CHANGE-*`。
10. 任務文件獨立變更的「來源 plan 變更」必須填寫「不適用」。
11. 原文位置必須包含里程碑、任務識別碼及欄位名稱。
12. 新增項目時，「修改前」記錄為「不存在」。
13. 刪除項目時，正文移除該項目，「修改前」保留完整內容，「修改後」記錄為「已刪除」。
14. 初次建立任務文件不視為變更，初版變更紀錄顯示「尚無變更」。
15. 純排版或不影響語意的錯字修正不需要建立變更紀錄。
16. 變更紀錄不得取代 Git 歷史。
17. 變更紀錄使用下列格式：

| 變更編號 | 日期 | 來源 plan 變更 | 原文位置 | 修改前 | 修改後 | 修改原因 | 受影響項目 |
|---|---|---|---|---|---|---|---|
| `CHANGE-003-TASK-1` | `YYYY-MM-DD` | `CHANGE-003` | `<里程碑／TASK／欄位>` | `<修改前內容>` | `<修改後內容>` | `<原因>` | `<識別碼>` |
| `TASK-CHANGE-001` | `YYYY-MM-DD` | 不適用 | `<里程碑／TASK／欄位>` | `<修改前內容>` | `<修改後內容>` | `<原因>` | `<識別碼>` |

## 15. 完整性檢查

1. 提交任務文件草案前，必須確認：
   1. 來源計畫存在且狀態為「已確認」。
   2. 檔名為 `./tasks/<plan-name>.md`。
   3. 所有里程碑依來源計畫順序出現。
   4. 所有交付成果與驗收標準都有任務涵蓋。
   5. 所有任務都有唯一且穩定的 `TASK-*`。
   6. 所有相依關係有效且沒有循環。
   7. 每個任務都包含全部必要欄位。
   8. 所有檔案路徑、步驟、命令、輸出及驗證均明確。
   9. 所有通過條件均可客觀判定。
   10. 文件中沒有未確認假設或要求執行 AI 自行決定的內容。
2. 任一檢查未通過時，不得宣稱草案完整或請求寫入檔案。
