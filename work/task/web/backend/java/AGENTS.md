# Java 後端任務規劃規範

## 1. 適用方式

1. 本規範用於根據已確認的來源計畫，產生或維護 Spring Boot 後端核心開發任務。
2. 使用本規範時，task hierarchy 必須依序包含：
   1. `general`
   2. `web`
   3. `web/backend`
   4. `web/backend/java`
3. 本規範只補充 Java 與 Spring Boot 特有要求。
4. 未涵蓋事項依 `general` 與 `backend` task 處理。
5. 若相同層級的規則衝突，以後載入的本規範為準。
6. 本規範只負責建立及維護 Java 後端任務文件，不得直接執行任務內容。
7. Java 後端任務必須讓執行 AI 能依固定步驟完成，不得要求其自行選擇架構、框架功能、實作路徑、檔案或驗證方式。

## 2. 適用範圍

1. 本規範只適用於 Spring Boot 後端專案。
2. Java、Spring Boot、建置工具及相依套件版本必須以目標專案現況為準。
3. 禁止自行升級版本、替換建置工具、引入新框架或改變技術基線。
4. 下列 Spring Boot 領域必須依來源計畫與專案現況判斷是否適用：
   1. Web。
   2. Validation。
   3. Data。
   4. Transaction。
   5. Security。
   6. Messaging。
5. 不適用的領域不得建立任務；任務中的 Java 後端驗證欄位仍須保留並說明不適用原因。
6. 部署、發布、基礎設施、執行環境佈建、監控及日常維運不屬於本規範範圍。

## 3. 專案現況檢查

1. 產生任務前，必須唯讀檢查目標專案的：
   1. Java 版本。
   2. Spring Boot 版本。
   3. Maven、Gradle 或其他既有建置工具及 wrapper。
   4. 已採用的 Spring 模組及必要依賴。
   5. 模組、source set、套件與檔案組織。
   6. 既有分層、命名慣例及依賴方向。
   7. API、業務與 persistence 模型及其轉換方式。
   8. 驗證、交易與例外處理方式。
   9. 測試結構、架構驗證方式及可用命令。
   10. 格式檢查、靜態分析、型別或編譯檢查命令。
2. 必須從專案既有檔案確認版本、工具、命令及慣例，不得依通用 Spring Boot 慣例自行推測。
3. 任務引用專案現況時，必須列出提供依據的精確檔案路徑及需要讀取的內容。
4. 現況與本規範的固定架構不一致時，必須停止並說明：
   1. 不一致位置。
   2. 對預計修改檔案、步驟及驗證的影響。
   3. 需要使用者決定的處理方式。
5. 使用者確認前，不得把全面架構改造、相容層或暫時性繞過方式加入任務。

## 4. 固定分層架構

1. Spring Boot 後端能力必須採用下列分層：
   1. `Controller`
   2. `Business Service`
   3. `Service`
   4. `Repository`
2. 依賴方向必須固定為：
   1. `Controller` → `Business Service`
   2. `Business Service` → `Service`
   3. `Service` → `Repository`
3. 禁止跨層呼叫，包括：
   1. `Controller` 直接呼叫 `Service`。
   2. `Controller` 直接呼叫 `Repository`。
   3. `Business Service` 直接呼叫 `Repository`。
4. 禁止下層反向依賴上層。
5. 任務必須列出每個新增或修改檔案所屬層級、責任及直接依賴。
6. 任務完成後的累積工作區必須符合固定依賴方向，不得以後續任務修正本任務引入的跨層或反向依賴。

## 5. 分層責任

1. `Controller` 負責：
   1. 對外 API 契約。
   2. Request 與 response 的接收及回傳。
   3. 輸入格式、必填值及基礎約束驗證。
   4. 將請求交由 `Business Service` 處理。
2. `Controller` 不得承擔使用案例編排、業務規則、交易邊界或資料存取。
3. `Business Service` 負責：
   1. 使用案例編排。
   2. 跨 `Service` 的業務流程。
   3. 使用案例及跨領域規則驗證。
   4. 交易邊界。
4. `Business Service` 只能透過 `Service` 使用領域與資料能力，不得直接存取 `Repository`。
5. `Service` 負責：
   1. 單一領域能力。
   2. 領域業務規則及狀態驗證。
   3. 封裝對 `Repository` 的資料操作需求。
6. `Service` 不得處理 HTTP request、response、使用案例編排或其他傳輸層責任。
7. `Repository` 只負責資料存取、持久化查詢、寫入能力及已確認的資料完整性要求。
8. `Repository` 不得承擔使用案例編排、業務流程、API 契約或傳輸層驗證。
9. 任務必須將每項行為、驗證及交易責任配置到唯一層級，不得要求執行 AI 自行判斷或在多層重複實作。

## 6. 資料模型隔離與轉換

1. 下列模型必須彼此隔離：
   1. API request 與 response。
   2. 業務模型。
   3. Persistence entity。
2. Persistence entity 不得直接作為 API request、response 或業務模型。
3. API request 或 response 不得直接作為業務模型或 persistence entity。
4. 業務模型不得直接作為 API request、response 或 persistence entity。
5. 任務必須明確列出：
   1. 各模型的責任與精確檔案。
   2. 模型間的轉換方向。
   3. 每個轉換的責任層級與精確檔案。
   4. 欄位、空值、驗證、預設值及相容性行為。
   5. 轉換的測試檔案、驗證方式及通過條件。
6. 轉換方式必須沿用專案既有慣例；不得自行引入新的 mapping 函式庫或程式碼產生工具。
7. 若完成單一成果所需的模型與轉換不可分割，必須置於同一任務並共同驗證。

## 7. 驗證、交易與錯誤責任

1. 驗證責任固定為：
   1. `Controller`：輸入格式、必填值及基礎約束。
   2. `Business Service`：使用案例及跨領域流程規則。
   3. `Service`：單一領域規則、狀態及操作條件。
2. 相同規則不得由多個層級重複負責。
3. 交易邊界固定由 `Business Service` 負責。
4. 涉及交易的任務必須明確列出：
   1. 交易開始與結束邊界。
   2. 交易內的固定操作順序。
   3. 成功後的資料狀態。
   4. 失敗時的 rollback 行為與資料狀態。
   5. 交易驗證的初始狀態、命令及客觀通過條件。
5. 禁止為了通過測試而在 `Controller`、`Service` 或 `Repository` 建立額外交易邊界。

## 8. 統一 API 錯誤契約

1. Spring Boot 後端必須提供統一且穩定的 API 錯誤契約。
2. 適用的任務必須明確列出：
   1. 驗證失敗、業務失敗及系統失敗的分類。
   2. 內部錯誤與 API 回應的固定映射。
   3. HTTP 狀態、對外錯誤識別碼及回應內容。
   4. 不得暴露的堆疊、內部實作、機密或敏感資訊。
   5. 預計修改的例外、錯誤模型及處理器精確檔案。
   6. 每一類錯誤的測試案例、預期回應及通過條件。
3. 錯誤契約必須沿用來源計畫與專案既有契約，不得自行重新命名或建立不相容格式。
4. 錯誤契約尚未確認且會影響實作時，任務不得標示為可執行。
5. 非 Web 任務仍須評估是否影響既有錯誤契約；不影響時須說明原因。

## 9. Spring Boot 領域任務

1. Web 適用時，任務必須明確列出：
   1. API 契約與消費者。
   2. Request、response、狀態碼及錯誤契約。
   3. 輸入驗證、權限及相容性要求。
   4. `Controller` 與 `Business Service` 的責任邊界。
2. Validation 適用時，任務必須將每項規則配置到 `Controller`、`Business Service` 或 `Service`，並列出成功與失敗案例。
3. Data 適用時，任務必須明確列出：
   1. Persistence entity 與 `Repository` 精確檔案。
   2. 資料所有權、關係、完整性及讀寫行為。
   3. 業務模型與 persistence entity 的轉換責任。
   4. 查詢、寫入與資料完整性驗證。
4. Transaction 適用時，必須依本規範固定由 `Business Service` 定義交易邊界，並驗證 commit 與 rollback 行為。
5. Security 適用時，任務必須明確列出身分驗證責任、授權規則、資源邊界、敏感資料限制及合法、未驗證、權限不足與跨資源存取案例。
6. Messaging 適用時，任務必須明確列出：
   1. 訊息契約及發布者與消費者責任。
   2. 序列化與業務模型的轉換邊界。
   3. 重複傳遞、排序、重試、冪等性及失敗行為。
   4. 固定測試方式與客觀通過條件。
7. Annotation、設定、類別或框架功能只能作為完成來源計畫成果所需的實作內容，不得單獨形成沒有可驗收行為的任務。

## 10. Java 後端任務拆解與排序

1. 任務必須依可獨立驗證的契約、使用案例、領域能力、資料能力或安全能力拆分，不得僅按四個架構層拆分。
2. 同一成果涉及多層修改且拆分後會造成編譯、測試或架構驗證失敗時，相關修改視為不可分割，必須置於同一最小任務。
3. 可分離且能維持綠燈狀態的下列成果必須拆成不同任務：
   1. API 或訊息契約。
   2. 使用案例能力。
   3. 領域能力。
   4. 資料存取能力。
   5. Schema migration 或既有資料轉換。
   6. 身分驗證或授權能力。
4. 每個任務完成後的累積工作區必須：
   1. 可成功編譯或建置。
   2. 通過受影響的既有與新增測試。
   3. 通過適用的格式檢查及靜態分析。
   4. 符合固定分層、模型隔離及依賴方向。
5. 不得建立必須等待後續任務才能恢復編譯、測試或架構驗證的中間狀態。
6. 可平行任務不得修改相同 Java 檔案、契約、模型、migration、設定或共享狀態。

## 11. 實作檔案與命令

1. 每個任務必須將預計新增或修改的檔案精確列至檔名。
2. 適用時，檔案清單必須區分：
   1. API 或訊息契約。
   2. `Controller`。
   3. `Business Service`。
   4. `Service`。
   5. `Repository`。
   6. API、業務及 persistence 模型。
   7. 模型轉換。
   8. 例外與錯誤處理。
   9. Schema 與 migration。
   10. 設定範本。
   11. 測試與架構驗證。
3. 禁止只列套件、模組、目錄或未解析的萬用字元。
4. 命令必須使用目標專案既有建置工具；專案提供 Maven Wrapper 或 Gradle Wrapper 時，必須使用 wrapper。
5. 每項命令必須列出：
   1. 執行目錄。
   2. 適用作業系統的完整命令與必要參數。
   3. 預期輸出或可觀察結果。
   4. 失敗時的停止條件。
6. 禁止自行假設 Maven 或 Gradle；建置工具與命令必須由專案現況確認。
7. 安裝套件、更新鎖定檔或引入依賴必須由來源計畫或使用者明確確認，並列入預計修改檔案與驗證。

## 12. 分層測試

1. 每個任務都必須評估下列測試，適用時列出精確測試檔案、命令、初始狀態、預期結果及通過條件：
   1. `Controller` 契約、輸入驗證、錯誤契約及權限測試。
   2. `Business Service` 使用案例、跨領域規則、交易 commit 與 rollback 測試。
   3. `Service` 領域規則、狀態及失敗行為單元測試。
   4. `Repository` 查詢、寫入及資料完整性整合測試。
   5. API、業務與 persistence 模型轉換測試。
   6. 必要的跨層整合測試。
2. 不適用的測試類型必須保留並說明與任務成果無關的具體原因。
3. 測試框架、fixture、mock、stub、container 或測試資料建立方式必須沿用專案既有慣例。
4. 禁止自行引入新的測試框架、測試函式庫或測試環境。
5. 測試必須同時驗證成功、已確認失敗行為及任務涉及的邊界條件。
6. 測試不得依賴執行順序、正式外部服務、真實機密資料或不可重現的共享狀態。

## 13. 架構驗證

1. 每個任務都必須評估固定分層、禁止跨層呼叫、禁止反向依賴及模型隔離是否受影響。
2. 專案已有架構驗證工具或測試時，任務必須：
   1. 列出精確設定或測試檔案。
   2. 使用專案既有命令執行驗證。
   3. 列出預期結果及客觀通過條件。
3. 專案沒有既有架構驗證工具時，不得自行引入 ArchUnit 或其他新依賴。
4. 沒有自動化架構驗證時，任務必須提供固定人工檢查程序，至少包含：
   1. 逐一檢查本任務新增或修改 Java 檔案的 package 與 import。
   2. 確認 `Controller` 只依賴 `Business Service`。
   3. 確認 `Business Service` 只透過 `Service` 使用領域與資料能力。
   4. 確認 `Service` 只透過 `Repository` 存取資料。
   5. 確認 `Repository` 未依賴任何上層。
   6. 確認 API、業務與 persistence 模型未互相直接取代。
5. 人工檢查必須列出待檢查的精確檔案、允許與禁止的依賴，以及逐檔可判定的通過條件。
6. 不得以「檢查架構是否正確」等未指定對象與判準的描述取代固定程序。

## 14. Java 後端驗證

1. 每個任務必須依固定順序驗證：
   1. 受影響範圍編譯或專案既有等效檢查。
   2. 受影響的既有測試。
   3. 本任務新增或修改的測試。
   4. 適用的格式檢查與靜態分析。
   5. 自動化或人工架構驗證。
2. 專案沒有獨立 compile 命令時，必須使用既有 build 命令；不得自行建立新的建置流程。
3. 每項驗證必須列出：
   1. 驗證對象。
   2. 初始狀態。
   3. 執行目錄與完整命令，或固定人工檢查步驟。
   4. 預期輸出。
   5. 客觀通過條件。
   6. 副作用及回復方式；沒有副作用時明確寫明「無」。
4. 任一驗證失敗時，任務必須要求執行 AI 立即停止、保留現況並回報失敗命令、實際輸出及已完成步驟，不得自行修改實作或改用其他命令重試。
5. 不得宣稱未實際執行的驗證已通過。

## 15. Java 後端風險

1. 除 `general` 與 `backend` task 的風險要求外，必須依任務評估：
   1. 既有架構與固定分層不一致。
   2. Java、Spring Boot、建置工具或依賴版本不明。
   3. 跨層呼叫或反向依賴。
   4. API、業務模型與 persistence entity 耦合。
   5. 模型轉換責任或資料相容性不明。
   6. 驗證或交易責任不清。
   7. 統一錯誤契約不一致或尚未確認。
   8. 現有測試無法驗證必要行為。
   9. 缺少自動化架構驗證而需依賴人工檢查。
2. 只有會實質影響成果、檔案、步驟、命令或驗證的風險才可納入。
3. 每項風險必須列出可能影響、可辨識的觸發條件及任務開始前需要成立的保護措施。
4. 禁止為了填滿欄位而建立假設性風險。

## 16. Java 後端任務就緒檢查

1. Java 後端任務提交草案前，除 `general` 與 `backend` task 的完整性檢查外，必須確認：
   1. 已確認 Java、Spring Boot、建置工具及必要依賴版本。
   2. 已列出所有預計新增或修改的精確檔案及所屬層級。
   3. 所有依賴均符合固定分層方向。
   4. API、業務與 persistence 模型彼此隔離。
   5. 所有模型轉換責任、檔案及驗證均已明列。
   6. 驗證、交易及錯誤處理責任均配置到固定層級。
   7. 統一 API 錯誤契約及適用驗證案例均已明列。
   8. 每個適用層級都有可執行的測試或明確的不適用原因。
   9. 已定義自動化或固定人工架構驗證。
   10. 編譯、測試、格式檢查、靜態分析及架構驗證命令均來自專案現況。
   11. 任務完成後的累積工作區可維持編譯、測試及架構驗證綠燈。
   12. 未引入未經確認的新依賴、框架、工具或技術基線。
2. 任一項未通過時，任務不得標示為可執行，且必須明確記錄缺少資訊與解除條件。
