# 後端任務規劃規範

1. 規劃前唯讀確認專案架構、測試慣例及可用工具；TASK 必須在 `決策` 明列本次採用的既有架構或已核准架構調整，並依通用欄位規則固定單一契約、責任邊界、資料、交易及錯誤行為，只記必要架構決策或核准例外。
2. 需要某測試的首個 TASK 必須同時建立或修改該測試與最小實作；測試只能來自目前基線、明確相依的前序 TASK 或目前 TASK，不得由後序或最終驗證 TASK 回補。
3. 可自動化的行為變更在同一 TASK 依序執行 Red、Green、Refactor；Red 與 Green 使用獨立 VAL 且可共用 CMD，Red 須預定目標測試及因功能未實作而失敗的條件。
4. Red 只是暫時狀態；TASK 完成時累積工作區必須通過全部適用驗證。
5. 可重現的相關測試放入實作 TASK；需資料庫、Redis、特定本機檔案或外部服務的完整回歸另建具明確前置條件的驗證 TASK。
6. 不得為通過驗證排除、停用、替換或延後必要測試；只列適用測試，高影響測試省略且原因不明顯時簡述原因。
7. 建立資料表或新增欄位的 TASK，必須要求每個新增資料表與欄位具備非空 comment，並固定 comment 內容及驗證方式；不得只為部分新增欄位提供 comment。
8. 新增或修改後端流程時，專案既有架構優先，TASK 必須在 `決策` 固定實際適用的依賴鏈路與各層責任；只有專案已採用四層架構，或使用者明確核准架構調整時，才適用下列 `Controller → 業務 Service → Persistence Service → 資料庫存取層` 完整鏈路及限制。無法確認既有架構時，先在對話提出四層方案並逐項取得確認，確認前維持草案；未觸及的既有程式不主動重構。
    1. Controller 只處理傳輸協定、輸入驗證、目前使用者資訊、請求／回應轉換及呼叫業務 Service，不得包含業務規則或直接呼叫其他層。可取得目前使用者資訊時，須依專案既有風格由 Controller 取得並傳入業務 Service；預設只傳用例所需的使用者 ID，業務確實需要時才能傳既有使用者物件。業務 Service 不得直接存取 Controller、HTTP Session 或安全框架上下文。
    2. 業務 Service 負責所有業務規則、用例流程、跨 Persistence Service 協調及交易邊界，不得直接查詢或持久化資料。
    3. Persistence Service 只封裝資料操作並呼叫資料庫存取層，不得包含業務規則、用例流程或交易邊界。
    4. 資料庫存取層只執行查詢與持久化，不得包含資料操作編排或業務邏輯。
9. TASK 選用前項四層架構時，各層的類別與介面命名優先遵循專案既有規範；沒有明確慣例時，將下列預設納入四層方案並取得確認，確認前維持草案。TASK 選用其他架構時，依該架構與專案既有命名固定，不套用下列四層預設：
    1. Controller 使用 `Controller` 後綴，前綴及端點分組粒度沿用專案風格。
    2. 業務 Service 使用 `Service` 後綴；若 `Service` 在專案中已代表封裝資料操作的層級，則使用 `BusinessService` 後綴。
    3. Persistence Service 使用 `PersistenceService` 後綴。
    4. 資料庫存取層使用 `Repository` 後綴。
    5. 介面不加 `I` 前綴，實作類別使用 `Impl` 後綴。
10. 套件與目錄結構優先遵循專案既有規範；TASK 選用四層架構且沒有明確慣例時，將先依技術分層再依功能分組的 `controller/<功能>`、`service/business/<功能>`、`service/persistence/<功能>` 及 `repository/<功能>` 納入方案並取得確認。其他架構須由 TASK 依既有結構固定，不得套用四層目錄預設。
11. 正式 TASK 核准前，須以唯讀探索逐項核對 TASK 預計建立、修改或移動的路徑，以及輸入與步驟引用的既有符號：
    1. 依目標模組的相鄰同類實作確認實際套件／目錄、命名、分層及測試位置，不得只依通用慣例推測。
    2. 確認引用的類別、介面、方法及設定實際存在，且位置、簽章、可見性與責任符合規劃用途。
    3. 區分符合既有結構而預計新增的路徑，與因錯誤假設而不存在或衝突的路徑；前者可列入 TASK，後者不得核准。
    4. 現況無法確認、與固定方案衝突，或必須改用其他路徑、符號或責任邊界時，維持對話草案並先完成確認，不得建立正式 TASK 後交由 execute 發現或修正 TASK。
12. TASK 涉及 Web 請求綁定、輸入驗證或例外回應契約時，正式核准前須依實際程式碼與設定追蹤 `請求 → 綁定／驗證 → 實際例外型別 → handler 選擇 → HTTP 狀態與回應內容`：
    1. 核對 Controller 參數與驗證註解、適用的 advice／handler、例外繼承與 handler 匹配條件，以及直接覆蓋該路徑的既有測試；不得只依名稱相近、簽章相似或同類 handler 的存在推測契約。
    2. TASK 固定的 HTTP 狀態、錯誤碼及回應結構須與目前實際處理路徑一致；需求確實要改變既有行為時，須將必要修改檔案列入範圍，並規劃能區分變更前後行為的 Red 與 Green VAL。
    3. 無法唯讀確認實際 handler 選擇或回應結果時維持對話草案；不得先固定推測契約，再交由 execute 判定或修改 TASK。
13. 每個 Red VAL 在正式 TASK 核准前須通過下列前置條件檢查：
    1. 固定目標測試類、專案相對路徑、所屬模組，以及其來源為目前基線、明確相依的前序 TASK 或目前 TASK。
    2. 目標測試引用的正式類別、介面、方法、錯誤碼與設定，須由目前基線、前序 TASK，或目前 TASK 在測試之前建立的最小可編譯骨架提供；不得依賴後序 TASK 或尚未規劃的產物。
    3. 目前 TASK 新增目標測試時，步驟須依序建立全部最小可編譯骨架、建立測試，再執行 Red 的 `CMD-*`；目標測試尚未存在或尚不可編譯時執行的基線命令，不得記為 Red 或用於通過 Red VAL。
    4. 任一測試來源、編譯前置、檔案操作或步驟順序尚未確認時，維持對話草案，不得以就緒檢查通過或建立正式 TASK。
