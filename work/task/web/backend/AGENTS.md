# 後端任務規劃規範

## 1. 適用方式

1. 本規範用於根據已確認的來源計畫，產生或維護後端核心開發任務。
2. 使用本規範前，必須先載入 `general` task，再載入 `backend` task。
3. 本規範只補充後端特有要求；未涵蓋事項依 `general` task 處理。
4. 若本規範與 `general` task 衝突，以後載入的本規範為準。
5. 任務規劃必須保持技術中立，除非來源計畫、專案現況或使用者已確認特定技術限制。
6. 本規範只負責建立及維護後端任務文件，不得直接執行任務內容。
7. 後端任務必須以讓能力較低的執行 AI 也能依規格一次正確完成為首要設計原則；不得依賴執行 AI 自行補充設計、選擇實作路徑或推測缺少資訊。

## 2. 核心範圍

1. 後端任務可涵蓋下列核心開發領域：
   1. 服務或模組的責任與邊界。
   2. API 或事件契約。
   3. 業務邏輯與錯誤處理。
   4. 資料模型與資料存取。
   5. schema、migration、必要資料轉換及回復驗證。
   6. 外部系統整合。
   7. 身分驗證、授權及核心安全需求。
   8. 與後端成果直接相關的測試及驗證。
2. 各領域必須依來源計畫及實際需求判斷是否適用。
3. 禁止為了涵蓋所有領域而建立來源計畫未要求的任務。
4. 不適用的領域不得強制建立任務。

## 3. 排除範圍

1. 下列工作不屬於 backend task 範圍：
   1. 部署與發布。
   2. 基礎設施建立或修改。
   3. 執行環境佈建。
   4. 監控平台或告警配置。
   5. 日常維運程序。
   6. 前端或用戶端實作。
   7. 第三方或其他內部服務的實作。
2. 後端成果依賴排除範圍內的工作時，只能記錄：
   1. 必要契約。
   2. 前置條件。
   3. 責任歸屬。
   4. 阻塞影響。
3. 排除範圍內的工作不得混入後端任務的執行步驟或驗證命令。

## 4. 後端需求釐清

1. 除 `general` task 的需求釐清項目外，必須依需求確認：
   1. 服務或模組的責任與邊界。
   2. 呼叫者、消費者及相依系統。
   3. 輸入、輸出、錯誤及失敗行為。
   4. 資料所有權、來源、生命週期及存取需求。
   5. 外部整合的責任、契約及失敗處理。
   6. 身分驗證、授權及敏感資料處理需求。
   7. 相容性與版本限制。
2. 下列品質屬性會影響成果、檔案、步驟或驗證時，必須完成確認：
   1. 一致性。
   2. 交易邊界。
   3. 冪等性。
   4. 排序。
   5. 重試與重複傳遞。
   6. 效能。
   7. 併發行為。
3. 必須以唯讀方式確認專案既有：
   1. 模組與服務邊界。
   2. 分層及命名慣例。
   3. API 或事件契約位置。
   4. 資料存取與 migration 慣例。
   5. 測試結構與可用命令。
   6. 格式檢查及靜態分析命令。
4. 無法從來源計畫及專案現況確定的必要資訊，必須逐題詢問使用者。
5. 禁止自行假設框架、資料庫、通訊協定、建置工具或測試工具。

## 5. AI 執行就緒門檻

1. 任務規劃必須優先最大化執行 AI 正確完成任務的成功率，不得為了縮短文件、減少任務數量或省略重複資訊而犧牲可執行性。
2. 任務只有同時符合下列條件，才能標示為可執行：
   1. 單一成果及客觀完成狀態已明確定義。
   2. 所有前置條件均可在執行前客觀確認。
   3. 所有輸入、初始狀態及固定版本均已明列。
   4. 所有預計修改的檔案均已精確至檔名。
   5. 實作方式只有一條已確認的固定路徑。
   6. 執行步驟使用固定順序，且每一步只包含一個明確動作。
   7. 每一步均列出可觀察的預期結果。
   8. 所有命令均包含執行目錄、完整命令、必要參數及預期輸出。
   9. 所有驗證方式及客觀通過條件均已明列。
   10. 所有具副作用操作均已標示影響及回復方式。
   11. 所有失敗停止條件均已明列。
   12. 任務中不存在未解析的佔位符、選項、分支或待確認事項。
   13. 任務已縮小至不可再拆分的單一可獨立驗證成果；若仍可拆出不影響其他部分驗收的成果，必須繼續拆分。
   14. 任務完成後的累積工作區可通過適用的編譯及測試驗證，不會留下必須等待後續任務才能恢復的失敗狀態。
3. 任務正文必須包含執行所需的全部已確認決策與資訊。
4. 任務可以引用其他檔案作為輸入，但必須列出精確路徑及需要讀取的內容；不得要求執行 AI 自行尋找相關檔案。
5. 任務不得要求執行 AI：
   1. 自行探索專案以決定修改範圍。
   2. 比較多種實作方案後自行選擇。
   3. 自行進行架構、契約、資料模型或安全設計。
   4. 自行推測缺少的需求、限制、檔案、命令或驗證方式。
   5. 在多條未指定選擇條件的路徑中自行判斷。
6. 任務不得使用「視情況」、「適當處理」、「依需要」、「相關檔案」、「執行時決定」或其他需要執行 AI 自行判斷的描述。
7. 任務步驟必須細分到執行 AI 可以依序照做，不需要在步驟之間作出新的技術決策。
8. 若任務仍需執行期間的技術判斷，必須繼續釐清或拆分，直到判斷已由任務規格預先決定。
9. 若缺少任何就緒條件，任務必須維持草案或標示為受阻，並明確記錄缺少資訊及解除條件。
10. 執行失敗時，任務必須要求執行 AI：
    1. 立即停止後續步驟。
    2. 保留目前狀態。
    3. 回報失敗命令、實際輸出及已完成步驟。
    4. 不得自行改用其他實作方式、命令或工具。

## 6. 任務拆解原則

1. 每個後端任務必須產生一個最小、單一、明確且可獨立驗證的成果。
2. 規劃時必須逐項判斷是否仍可拆出能獨立實作、驗證、失敗或重新執行的成果；只要可以，就必須拆成不同任務。
3. 只有為了完成及驗證同一成果而不可分割的程式碼、契約、資料修改、測試、格式檢查及靜態分析，才能包含於同一任務。
4. 任務大小不得以檔案數量決定；修改多個檔案若是同一成果不可分割的必要部分，可以保留在同一任務。
5. 任務不得包含「順便處理」、可延後處理或不影響該成果驗收的修改。
6. 下列成果可以獨立驗收時，必須拆成不同任務：
   1. 契約新增或修改。
   2. 業務能力實作。
   3. 資料模型或資料存取修改。
   4. schema migration。
   5. 既有資料轉換。
   6. 外部系統整合。
   7. 身分驗證或授權修改。
7. 不得將不同服務、模組或責任邊界的可分離成果合併為一個任務。
8. 任務涉及跨系統工作時，只能包含本後端責任範圍內的修改。
9. 相依系統的工作必須記錄為前置條件或外部依賴，不得納入後端任務步驟。
10. 任務順序必須反映契約、資料、實作及驗證之間的真實相依關係。
11. 可平行執行的任務必須確認不會修改相同檔案、schema、契約或共享狀態。

## 7. 任務排序與綠燈檢查點

1. 任務必須依相依關係排序，使每個任務完成後的累積工作區都維持可編譯、可測試及可驗證的狀態。
2. 每個任務的驗證基準為：
   1. 該任務的所有相依任務均已完成。
   2. 工作區包含所有已完成前序任務的累積變更。
   3. 不依賴尚未執行的後續任務才能通過驗證。
3. 每個任務完成後必須驗證：
   1. 受影響範圍可成功編譯。
   2. 與變更相關的既有測試全部通過。
   3. 該任務新增或修改的測試全部通過。
   4. 適用的格式檢查、靜態分析及型別檢查全部通過。
4. 任務不得產生下列中間狀態：
   1. 契約已變更但必要實作尚未相容，造成編譯或測試失敗。
   2. schema 已變更但資料存取程式碼尚未相容。
   3. 呼叫端已修改但被呼叫端尚未提供必要能力。
   4. 測試已修改但對應實作必須等待後續任務才能完成。
   5. 暫時停用測試、降低檢查標準或加入無效實作以通過驗證。
5. 契約、migration、資料模型及實作可以拆成不同任務時，必須使用向後相容的修改方式及正確排序，確保每個完成點均維持綠燈狀態。
6. 若無法在拆分後維持每個完成點可編譯及可測試，相關修改視為同一成果的不可分割部分，必須合併於同一最小任務。
7. 專案沒有獨立 compile 命令時，必須依序採用專案既有的等效驗證：
   1. build。
   2. 型別檢查。
   3. 語法檢查。
8. 專案沒有自動化 test 命令時，任務必須：
   1. 明確說明缺少自動化測試的原因。
   2. 提供固定步驟的人工驗證程序。
   3. 列出預期結果及客觀通過條件。
9. 任務文件的執行順序摘要必須反映上述編譯、測試及相容性依賴，不得只依功能或檔案順序排列。
10. 任一任務無法定義完成後的綠燈驗證時，不得標示為可執行。
11. 具有可自動化測試的行為變更必須在同一最小任務內依序採用下列 TDD 流程：
    1. 確認任務範圍、預期行為及驗收條件均已釐清並固定。
    2. Red：先建立或修改能表達預期行為的測試，並執行該測試確認其因尚未具備對應功能而失敗。
    3. Green：完成使該測試通過所需的最小實作，並執行相關測試確認通過。
    4. Refactor：只有在有明確必要時才進行最小重構，且不得改變已驗證的行為。
    5. 執行該任務適用的完整測試、編譯、格式檢查、靜態分析及型別檢查。
12. Red 階段執行測試前，必須明確記錄預期失敗的測試、失敗條件及失敗原因。
13. Red 階段只有在新增或修改的測試依事先定義的條件及原因失敗時，才可視為預期失敗並繼續進入 Green；此預期失敗不適用一般測試失敗後必須停止的規則。
14. Red 階段若出現既有測試失敗、編譯錯誤、環境錯誤或任何不符合預期條件及原因的失敗，必須立即停止並回報，不得進入實作。
15. 測試、對應實作及必要重構不得拆分為會使任一已完成任務處於失敗狀態的不同任務；Red 只允許作為同一最小任務內的暫時狀態。
16. Refactor 完成後必須重新執行 Green 階段已通過的相關測試，以及該任務適用的完整驗證。
17. 文件、純設定、無行為影響的格式修改或其他沒有適用自動化測試的變更可以不採用 TDD，但任務文件必須明確記錄原因及固定的替代驗證方式。

## 8. API 與事件契約任務

1. 適用時，任務必須明確列出：
   1. 契約的用途與消費者。
   2. 輸入與輸出的必要行為。
   3. 錯誤與失敗行為。
   4. 權限要求。
   5. 相容性或版本限制。
   6. 預計修改的契約檔案。
2. 若適用，任務必須處理：
   1. 冪等性。
   2. 排序。
   3. 重試。
   4. 重複傳遞。
   5. 向後相容性。
3. 契約修改與消費者實作可獨立驗收時，必須拆成不同任務。
4. 任務不得包含其他服務或用戶端的具體實作。
5. 契約驗證必須使用專案既有工具或明確人工檢查程序。

## 9. 資料與 migration 任務

1. 適用時，任務必須明確列出：
   1. 資料所有權。
   2. 核心資料關係。
   3. 完整性與一致性要求。
   4. 讀取及寫入責任。
   5. 交易邊界。
   6. 資料生命週期。
2. schema、migration 或資料轉換任務必須列出：
   1. 預計新增或修改的精確檔案。
   2. migration 的固定執行順序。
   3. 適用的前置資料狀態。
   4. 預期 schema 或資料結果。
   5. 失敗時的回復方式。
   6. 回復方式的驗證程序。
3. migration 具有不可逆風險時，必須：
   1. 明確記錄不可逆部分。
   2. 說明可能影響的資料。
   3. 將必要備份或人工保護程序列為前置條件。
   4. 不得要求 AI 執行破壞性資料操作。
4. 生產資料操作不得列為 AI 可直接執行的命令。
5. 任務不得讀取、顯示、寫入或傳送真實機密資料。
6. migration 驗證如會改變資料或外部狀態，必須明列為具副作用操作。

## 10. 外部系統整合任務

1. 適用時，任務必須明確列出：
   1. 整合目的。
   2. 系統間責任邊界。
   3. 輸入、輸出及錯誤行為。
   4. 認證與授權方式。
   5. 已確認的相容性限制。
   6. 超時、重試及失敗處理。
2. 不得自行假設外部系統能力、可用性或契約。
3. 外部依賴尚未確認且會影響實作時，不得將任務規格標示為可執行。
4. 任務驗證不得依賴未經授權的正式外部服務操作。
5. 可使用 mock、stub、sandbox 或測試環境時，必須明確指定已確認的驗證目標與方式。
6. 任何外部服務連線或狀態變更都必須明列於外部操作。

## 11. 核心安全任務

1. 適用時，任務必須明確列出：
   1. 身分驗證責任。
   2. 授權規則與資源邊界。
   3. 敏感資料處理限制。
   4. 不可信輸入的驗證需求。
   5. 越權與資料暴露風險。
2. 安全需求必須轉換成可執行的驗證方式及客觀通過條件。
3. 權限修改必須驗證：
   1. 合法存取。
   2. 未驗證存取。
   3. 權限不足存取。
   4. 跨資源或跨租戶存取。
4. 不適用的安全驗證必須在任務中說明原因。
5. 任務文件不得包含密碼、API 金鑰、存取權杖、私鑰或其他機密資料。
6. 驗證需要機密資料時，必須要求使用者以安全方式自行設定，不得要求將值寫入任務文件或命令。

## 12. 實作檔案與命令

1. 每個任務必須將預計修改的檔案精確列至檔名。
2. 適用時，檔案清單應區分：
   1. 契約。
   2. 應用程式程式碼。
   3. 資料模型與資料存取。
   4. schema 與 migration。
   5. 設定範本。
   6. 測試。
   7. 文件。
3. 禁止只列目錄、模組名稱或未解析的萬用字元。
4. 命令必須使用專案現有工具及既有慣例。
5. 每項命令必須包含：
   1. 執行目錄。
   2. 完整命令。
   3. 必要參數。
   4. 預期輸出或可觀察結果。
6. 安裝套件、更新鎖定檔或引入新依賴必須明確列入任務。
7. 未經來源計畫或使用者確認，不得自行引入新的框架、資料庫、服務或技術。
8. 部署、發布、基礎設施、監控配置及維運命令不得列入後端任務。

## 13. 後端驗證

1. 每個任務都必須評估下列驗證類型：
   1. 單元驗證。
   2. 整合驗證。
   3. API 或事件契約驗證。
   4. 資料完整性與 migration 驗證。
   5. 身分驗證與授權驗證。
   6. 已確認品質屬性的驗證。
2. 適用的驗證類型必須列出可實際執行的命令或明確人工檢查程序。
3. 不適用的驗證類型必須保留並簡短說明原因。
4. 每項驗證必須明確列出：
   1. 驗證對象。
   2. 初始狀態。
   3. 執行方式。
   4. 預期結果。
   5. 客觀通過條件。
5. 驗證範圍必須與任務修改範圍相符。
6. 適用時，任務必須包含專案既有的：
   1. 測試命令。
   2. 格式檢查。
   3. 靜態分析。
   4. 型別檢查。
   5. 建置驗證。
7. 不得宣稱未實際執行的驗證已通過。
8. 驗證會修改資料、本機狀態或外部狀態時，必須在任務中明確標示其副作用及回復方式。

## 14. 後端任務風險

1. 除 `general` task 的風險規則外，應依需求評估：
   1. 服務或模組責任邊界不清。
   2. API 或事件契約尚未確認。
   3. 相容性要求不明。
   4. 資料所有權或一致性要求不明。
   5. migration 不可逆或造成資料遺失。
   6. 交易邊界或併發行為不明。
   7. 外部整合能力或責任未確認。
   8. 身分驗證、授權或敏感資料處理需求不明。
   9. 測試環境無法重現必要行為。
2. 只有會實質影響任務成果、檔案、步驟、命令或驗證的風險才可納入。
3. 每項風險必須說明：
   1. 可能影響。
   2. 可辨識的觸發條件。
   3. 任務開始前需要成立的保護措施。
4. 禁止為了填滿欄位而建立假設性風險。
