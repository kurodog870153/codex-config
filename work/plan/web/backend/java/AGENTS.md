# Java 後端計畫規劃規範

## 1. 適用方式

1. 本規範用於根據 big picture 產生或維護 Spring Boot 後端核心開發計畫。
2. 使用本規範時，plan hierarchy 必須依序包含：
   1. `general`
   2. `web`
   3. `web/backend`
   4. `web/backend/java`
3. 本規範只補充 Java 與 Spring Boot 特有要求。
4. 未涵蓋事項依 `general` 與 `backend` plan 處理。
5. 若相同層級的規則衝突，以後載入的本規範為準。
6. 本規範不得直接執行計畫內容或展開成 task。

## 2. 適用範圍

1. 本規範只適用於 Spring Boot 後端專案。
2. Java、Spring Boot、建置工具及相依套件版本必須以目標專案現況為準。
3. 禁止自行升級版本、替換建置工具或引入新的技術基線。
4. 下列 Spring Boot 領域應依專案與需求判斷是否適用：
   1. Web。
   2. Validation。
   3. Data。
   4. Transaction。
   5. Security。
   6. Messaging。
5. 只有會影響目標、範圍、交付成果、里程碑或驗收的領域才能納入計畫。
6. 不適用的領域必須簡短說明原因，不得虛構需求或成果。
7. 部署、發布、基礎設施及日常維運不屬於本規範範圍。

## 3. 專案現況檢查

1. 產生計畫前，必須唯讀檢查目標專案的：
   1. Java 版本。
   2. Spring Boot 版本。
   3. Maven、Gradle 或其他既有建置工具。
   4. 已採用的 Spring 模組及必要依賴。
   5. 模組與套件組織。
   6. 既有分層與依賴方向。
   7. 資料模型與轉換方式。
   8. 驗證與例外處理方式。
   9. 測試結構與驗證慣例。
2. 檢查只用於辨識已確認的專案現況，不得將推測寫成限制或前提。
3. 若現況與本規範要求不一致，必須：
   1. 說明差異。
   2. 說明對範圍、成果及驗收的影響。
   3. 列入「待確認事項」。
   4. 在使用者確認前維持計畫為草案。
4. 禁止自行將全面架構改造納入計畫。

## 4. 固定分層架構

1. Spring Boot 後端能力必須採用下列分層：
   1. `Controller`
   2. `Business Service`
   3. `Service`
   4. `Repository`
2. 依賴方向必須固定為：
   1. `Controller` → `Business Service`
   2. `Business Service` → `Service`
   3. `Service` → `Repository`
3. 禁止跨層呼叫，包括：
   1. `Controller` 直接呼叫 `Service`。
   2. `Controller` 直接呼叫 `Repository`。
   3. `Business Service` 直接呼叫 `Repository`。
4. 禁止下層反向依賴上層。
5. 計畫只定義分層責任、邊界成果與驗收方式，不指定類別、套件或檔案實作。

## 5. Controller

1. `Controller` 負責：
   1. 對外 API 契約。
   2. Request 與 response 的接收及回傳。
   3. 輸入格式與基礎驗證。
   4. 將請求交由 `Business Service` 處理。
2. `Controller` 不得承擔：
   1. 使用案例編排。
   2. 業務規則。
   3. 交易邊界。
   4. 資料存取。
3. 適用時，計畫必須定義 API 行為、錯誤契約、權限要求及相容性成果。

## 6. Business Service

1. `Business Service` 負責：
   1. 使用案例編排。
   2. 跨 `Service` 的業務流程。
   3. 流程層級的業務規則驗證。
   4. 交易邊界。
2. `Business Service` 只能透過 `Service` 使用領域能力或資料能力。
3. `Business Service` 不得直接存取 `Repository`。
4. 適用時，計畫必須定義流程結果、交易一致性及失敗行為。

## 7. Service

1. `Service` 負責：
   1. 單一領域能力。
   2. 領域業務規則。
   3. 領域層級的業務驗證。
   4. 封裝對 `Repository` 的資料操作需求。
2. `Service` 不得處理 HTTP request、response 或其他傳輸層責任。
3. `Service` 不得繞過既有責任邊界存取其他層。
4. 適用時，計畫必須定義領域行為、資料一致性及可驗收結果。

## 8. Repository

1. `Repository` 負責：
   1. 資料存取。
   2. 持久化查詢與寫入能力。
   3. 維持已確認的資料完整性需求。
2. `Repository` 不得承擔：
   1. 使用案例編排。
   2. 業務流程。
   3. API 契約。
   4. 傳輸層驗證。
3. 計畫不得展開資料表、欄位、索引、查詢或遷移指令等實作細節。

## 9. 資料模型隔離

1. 下列模型必須隔離：
   1. API request 與 response。
   2. 業務模型。
   3. Persistence entity。
2. Persistence entity 不得直接暴露為 API request 或 response。
3. API 模型不得直接作為 persistence entity。
4. 計畫必須依需求定義：
   1. 各模型的責任邊界。
   2. 必要的資料轉換邊界。
   3. 契約及資料相容性要求。
5. 計畫不得指定轉換類別、函式庫或程式碼實作。

## 10. 驗證責任

1. `Controller` 負責：
   1. 輸入格式驗證。
   2. 必填值及基礎約束驗證。
2. `Business Service` 負責：
   1. 使用案例層級的業務驗證。
   2. 跨領域流程規則驗證。
3. `Service` 負責：
   1. 單一領域規則驗證。
   2. 領域狀態與操作條件驗證。
4. 相同規則不得在多層重複定義責任。
5. 計畫必須說明適用驗證的責任層級與客觀驗收結果。

## 11. 例外與錯誤契約

1. Spring Boot 後端必須提供統一且穩定的 API 錯誤契約。
2. 計畫必須依需求定義：
   1. 可對外識別的錯誤類型。
   2. 錯誤與 API 回應的對應成果。
   3. 驗證失敗、業務失敗及系統失敗的責任邊界。
   4. 不得暴露的內部或敏感資訊。
3. 計畫不得指定例外類別名稱、處理器類別或實作方式。

## 12. Spring Boot 領域規劃

1. Web 適用時，必須規劃：
   1. API 契約。
   2. 輸入驗證。
   3. 錯誤契約。
   4. 相容性要求。
2. Data 適用時，必須規劃：
   1. 資料所有權。
   2. 資料完整性。
   3. 讀寫責任。
   4. 一致性需求。
3. Transaction 適用時，必須規劃：
   1. 交易邊界。
   2. 成功與失敗結果。
   3. 回復或一致性要求。
4. Security 適用時，必須規劃：
   1. 身分驗證責任。
   2. 授權規則。
   3. 資源邊界。
   4. 敏感資料限制。
5. Messaging 適用時，必須規劃：
   1. 訊息契約。
   2. 發布者與消費者責任。
   3. 重複傳遞、排序、重試與冪等性需求。
   4. 失敗行為。
6. 每個領域只規劃成果、責任、限制及驗收，不指定 Spring annotation、設定檔或實作細節。

## 13. Java 後端交付成果

1. 除 `general` 與 `backend` plan 的要求外，交付成果應依需求包含：
   1. 符合固定分層與依賴方向的後端能力。
   2. 分層責任明確的使用案例與領域能力。
   3. 隔離 API、業務及 persistence 模型的資料契約。
   4. 統一且可驗證的錯誤契約。
   5. 符合既有版本與專案慣例的 Spring Boot 成果。
2. 只有適用的成果才能納入。
3. 框架、annotation、類別、套件或技術活動不得單獨作為交付成果。

## 14. Java 後端驗收證據

1. 每項交付成果必須要求適用且可觀察的驗證證據。
2. 驗證證據應依成果包含：
   1. `Controller` 契約與基礎驗證測試。
   2. `Business Service` 使用案例及交易行為測試。
   3. `Service` 領域規則單元測試。
   4. `Repository` 資料存取整合測試。
   5. 必要的跨層整合測試。
3. 必須驗證固定依賴方向及禁止跨層呼叫的架構要求。
4. 測試類型只在與成果相關時納入。
5. Plan 不得指定測試框架、測試檔案、測試命令或測試實作。

## 15. Java 後端里程碑

1. 里程碑應依可驗收的使用案例、領域能力或契約成果拆分。
2. 每個里程碑必須標示：
   1. 涉及的架構層。
   2. 預期交付成果。
   3. 必要的前置依賴。
   4. 適用的分層驗收證據。
3. 里程碑不得依 Controller、Business Service、Service 或 Repository 個別拆分。
4. 里程碑不得只以技術層、框架設定或程式活動命名。
5. 部署、發布與維運活動不得作為 Java 後端里程碑。

## 16. Java 後端風險

1. 除 `general` 與 `backend` plan 的風險要求外，應依需求評估：
   1. 既有架構與固定分層不一致。
   2. Java、Spring Boot 或依賴版本不明。
   3. 跨層呼叫或反向依賴。
   4. API、業務模型與 persistence entity 耦合。
   5. 交易邊界或業務驗證責任不清。
   6. 錯誤契約不一致。
   7. 現有測試無法提供必要驗收證據。
2. 只有會實質影響目標、範圍、交付成果、里程碑或驗收的風險才可納入。
3. 禁止為了填滿章節而虛構風險。
