# 計畫規劃規範

## 1. 適用範圍

1. 本規範用於將使用者提供的 big picture 轉換成通用、可驗收且可維護的高階計畫。
2. 本規範適用於新計畫的建立及既有計畫的維護。
3. 計畫文件統一存放於專案根目錄的 `./plans/`。
4. 計畫檔名必須使用小寫 kebab-case，格式為 `./plans/<plan-name>.md`。
5. AI 必須根據計畫名稱提出檔名，經使用者確認後才能採用。
6. 計畫文件應跟隨使用者描述 big picture 時使用的主要語言。
7. 使用者另有指定語言時，以使用者指定為準。

## 2. 職責邊界

1. 計畫規劃負責定義：
   1. 要達成什麼。
   2. 為什麼需要達成。
   3. 哪些內容屬於或不屬於計畫範圍。
   4. 需要交付哪些成果。
   5. 如何判斷計畫成功。
   6. 計畫分成哪些里程碑。
   7. 里程碑之間有哪些依賴關係。
2. 計畫規劃只列出里程碑所需的高階工作項目。
3. 高階工作項目不得展開成具體執行步驟、檔案修改、命令或實作細節。
4. 任務與子任務的拆解應交由適用的 task 規劃處理；task 規範可能位於目前專案或其他專案，不得預設固定路徑。
5. 本規範不得直接執行計畫內容。

## 3. 需求釐清

1. 產生計畫前，必須確認：
   1. 背景與需求。
   2. 目標與預期成果。
   3. 成功條件。
   4. 範圍與非目標。
   5. 交付成果。
   6. 驗收方式。
   7. 已確認的限制與前提。
   8. 里程碑所需的依賴關係。
   9. 負責人是否影響計畫執行或驗收。
   10. 使用者是否有期限或時程要求。
2. 關鍵資訊不足時，必須逐題詢問使用者。
3. 每次只能提出一個問題。
4. 每個問題必須提供明確且有編號的選項。
5. 必須標示建議選項並簡短說明理由。
6. 收到回答後，必須更新並重述目前已確認的需求。
7. 禁止自行建立未經使用者確認的假設。
8. 尚有會影響目標、範圍、交付成果、里程碑或驗收標準的待確認事項時，只能產生草案。
9. 所有待確認事項完成，不代表計畫已獲使用者核准。

## 4. 計畫必要內容

1. 每份計畫必須包含：
   1. 基本資訊。
   2. 需求摘要。
   3. 目標與成功條件。
   4. 範圍與非目標。
   5. 已確認的限制與前提。
   6. 交付成果。
   7. 驗收標準。
   8. 里程碑。
   9. 里程碑依賴與順序。
   10. 風險。
   11. 變更紀錄。
   12. 完成檢查。
2. 尚有未確認事項的草案，必須另外包含「待確認事項」。
3. 不適用的必要章節必須保留，並簡短說明不適用原因。
4. 禁止為了填滿章節而虛構內容。

## 5. 基本資訊

1. 計畫開頭必須使用 Markdown 資訊表。
2. 資訊表至少包含：

| 欄位 | 說明 |
|---|---|
| 計畫名稱 | 清楚描述計畫主題 |
| 狀態 | 使用本規範定義的整體計畫狀態 |
| 建立日期 | 使用 `YYYY-MM-DD` |
| 最後更新日期 | 使用 `YYYY-MM-DD` |
| 負責人 | 已確認的負責人，或「尚未指定」 |

3. AI 不得自行推定負責人。
4. 負責人尚未指定，不會單獨阻止計畫進入「已確認」。
5. 若負責人會實質影響計畫執行或驗收，必須列入待確認事項。

## 6. 整體計畫狀態

1. 計畫只能使用下列狀態：
   1. 草案：仍在規劃、釐清或等待核准。
   2. 已確認：使用者已明確核准整份計畫。
   3. 進行中：計畫已開始執行。
   4. 受阻：重大阻礙使計畫無法繼續。
   5. 已完成：所有交付成果與整體驗收標準均已通過。
   6. 已取代：已有另一份計畫正式取代本計畫。
2. AI 不得自行將計畫從「草案」改為「已確認」。
3. 只有使用者明確核准整份計畫後，才能使用「已確認」。
4. 任何狀態變更都必須先取得使用者確認。
5. 將計畫標示為「受阻」時，必須說明阻礙及解除條件。
6. 將計畫標示為「已取代」時，必須指出取代本計畫的新計畫。

## 7. 穩定識別碼

1. 下列項目必須配置唯一且穩定的識別碼：
   1. 目標：`GOAL-001`。
   2. 成功條件：`SUCCESS-001`。
   3. 交付成果：`DELIVERABLE-001`。
   4. 驗收標準：`ACCEPTANCE-001`。
   5. 里程碑：`MILESTONE-001`。
   6. 風險：`RISK-001`。
2. 識別碼必須依類型使用三位數流水號。
3. 識別碼建立後不得變更。
4. 項目重新排序或重新命名時，不得變更識別碼。
5. 刪除項目的識別碼永久保留，不得重新使用。
6. 新項目必須使用該類型下一個未使用的流水號。
7. 識別碼用於正文、依賴關係、驗收對應及變更紀錄定位。

## 8. 需求摘要

1. 必須以簡潔文字重述：
   1. 背景。
   2. 要解決的問題或機會。
   3. 預期產生的結果。
2. 不得加入使用者未確認的需求或推論。
3. 若摘要與使用者原始描述存在差異，必須先請使用者確認。

## 9. 目標與成功條件

1. 目標必須描述計畫完成後要達成的結果。
2. 成功條件必須能用證據判斷是否成立。
3. 必須區分：
   1. 目標：希望達成的結果。
   2. 成功條件：判斷整體計畫是否成功的依據。
4. 每個目標與成功條件都必須配置穩定識別碼。
5. 成功條件必須指出其對應的目標識別碼。
6. 禁止只使用「改善」、「完善」、「最佳化」或「提升」等無法判定的描述。

## 10. 範圍與非目標

1. 範圍必須列出本計畫包含的成果或責任。
2. 非目標必須列出明確排除的事項。
3. 非目標不是待辦事項，不得暗示一定會在後續納入。
4. 範圍變更前必須取得使用者確認。

## 11. 已確認的限制與前提

1. 本章只記錄經使用者確認的條件。
2. 可包含：
   1. 預算。
   2. 期限。
   3. 技術或平台限制。
   4. 法規或政策要求。
   5. 資源限制。
   6. 不可變更的決策。
3. 禁止將未確認的推測寫成限制或前提。
4. 若必要條件仍未確認，應放入「待確認事項」，計畫維持草案。

## 12. 交付成果

1. 每項交付成果必須：
   1. 配置穩定識別碼。
   2. 具體。
   3. 可檢查。
   4. 可移交。
   5. 對應至少一個目標識別碼。
   6. 具備客觀驗收標準。
2. 禁止將活動本身當成交付成果。
3. 若成果偏主觀，必須指定評審者、評審方式及通過門檻。

## 13. 驗收標準

1. 整體計畫、每項交付成果及每個里程碑都必須有客觀、可驗證的驗收標準。
2. 每項驗收標準必須配置穩定識別碼。
3. 驗收標準必須說明：
   1. 驗證對象。
   2. 驗證方式。
   3. 預期結果。
   4. 通過條件。
4. 驗收標準必須指出其對應的目標、交付成果或里程碑識別碼。
5. 禁止只使用「適當」、「正常」、「完整」、「高品質」或「視情況」等主觀描述。
6. 無法量化的成果必須使用明確評審規則取代模糊判斷。

## 14. 里程碑

1. 計畫必須依成果或邏輯階段拆分里程碑。
2. 每個里程碑必須配置穩定識別碼。
3. 每個里程碑必須包含：
   1. 目標。
   2. 預期成果。
   3. 高階工作項目。
   4. 前置依賴。
   5. 客觀驗收標準。
4. 里程碑不記錄狀態。
5. 高階工作項目只說明需要完成哪些工作，不展開成任務或子任務。
6. 每個里程碑必須產生可驗收的進展，不得只以時間區段命名。
7. 里程碑應依依賴關係及合理執行順序排列。

## 15. 時程規劃

1. 只有使用者提供期限或明確要求規劃時程時，才能加入日期。
2. 使用者只提供最終期限時，AI 可以提出里程碑日期建議。
3. 所有建議日期必須明確標示為「建議」，不得視為承諾。
4. AI 必須逐項取得使用者確認，才能將建議日期寫入正式計畫。
5. 未確認的日期只能存在於對話草案。
6. 使用者沒有期限或時程需求時，只記錄里程碑依賴與順序。

## 16. 依賴與順序

1. 必須使用識別碼標示會影響里程碑開始或完成的前置條件。
2. 必須說明里程碑之間的必要順序。
3. 可以指出可平行進行的里程碑。
4. 不得在缺少依據時自行建立外部依賴。

## 17. 風險

1. 每份計畫都必須包含風險章節。
2. 只記錄會實質影響目標、範圍、交付成果或驗收的重大風險。
3. 每項風險必須配置穩定識別碼。
4. 每項風險必須包含：
   1. 風險內容。
   2. 可能造成的影響。
   3. 發生可能性。
   4. 觸發條件。
   5. 應對方式。
5. 若沒有已知重大風險，必須寫明「目前無已知重大風險」。
6. 禁止為了填滿章節而虛構風險。

## 18. 檔名確認

1. AI 必須根據計畫名稱提出小寫 kebab-case 檔名。
2. 建議檔名格式為 `./plans/<plan-name>.md`。
3. 使用者確認檔名後才能採用。
4. 未確認前，只能在對話草案中使用建議檔名。
5. 禁止覆寫同名計畫檔案。
6. 若檔案已存在，必須先請使用者決定要更新既有計畫或改用其他名稱。

## 19. 草案與寫入流程

1. AI 必須先在對話中提供完整計畫草案。
2. 使用者核准前，不得建立或修改 `./plans/<plan-name>.md`。
3. 草案必須標示為「草案」。
4. 使用者明確核准整份草案後，才能：
   1. 將狀態改為「已確認」。
   2. 提出寫入計畫檔案的最小任務。
5. 寫入檔案前仍須取得使用者明確執行授權。

## 20. 計畫維護

1. 本規範負責核准後的計畫維護。
2. 可維護的內容包含：
   1. 整體計畫狀態。
   2. 需求摘要。
   3. 目標與成功條件。
   4. 範圍與非目標。
   5. 限制與前提。
   6. 交付成果。
   7. 驗收標準。
   8. 里程碑。
   9. 時程。
   10. 依賴與順序。
   11. 風險。
   12. 變更紀錄。
3. 所有內容變更都必須在執行前取得使用者確認。
4. 不得因計畫維護而自行拆解、修改或執行具體任務。
5. 需求變更若影響目標、範圍、交付成果、里程碑或驗收標準，必須重新提交相關內容供使用者確認。

## 21. 變更紀錄

1. 修改計畫內容時，必須直接更新原章節，使正文永遠代表目前有效版本。
2. 不得只新增變更紀錄而保留已失效的正文。
3. 每筆語意變更必須保留：
   1. 變更編號。
   2. 日期。
   3. 原文位置。
   4. 修改前內容。
   5. 修改後內容。
   6. 修改原因。
   7. 受影響項目。
4. 變更編號格式為 `CHANGE-001`，並依序遞增。
5. 已使用的變更編號不得變更或重複使用。
6. 原文位置必須同時包含章節名稱與穩定識別碼，例如 `里程碑 / MILESTONE-001 / 驗收標準 / ACCEPTANCE-003`。
7. 「修改前」與「修改後」只保存實際變更的完整欄位或條目。
8. 紀錄內容必須保留足以獨立理解變更的完整語意。
9. 同一次修改涉及多個欄位時，每個欄位必須分開記錄。
10. 新增項目時：
    1. 修改前記錄為「不存在」。
    2. 修改後記錄新增的完整欄位或條目。
11. 刪除項目時：
    1. 正文移除該項目。
    2. 修改前保留被刪除的完整欄位或條目。
    3. 修改後記錄為「已刪除」。
12. 初次建立計畫不視為變更。
13. 初版計畫的變更紀錄必須顯示「尚無變更」。
14. 第一次語意變更才建立 `CHANGE-001`。
15. 純排版或不影響語意的錯字修正不需要記錄，但仍應直接修正正文。
16. 變更紀錄不得取代 Git 歷史。
17. 變更紀錄使用下列格式：

| 變更編號 | 日期 | 原文位置 | 修改前 | 修改後 | 修改原因 | 受影響項目 |
|---|---|---|---|---|---|---|
| `CHANGE-001` | `YYYY-MM-DD` | `<章節／識別碼／欄位>` | `<修改前內容>` | `<修改後內容>` | `<原因>` | `<識別碼>` |

## 22. 完成檢查

1. 將整體計畫標記為「已完成」前，必須確認：
   1. 所有交付成果均已產出。
   2. 所有交付成果的驗收標準均已通過。
   3. 整體成功條件均已成立。
   4. 所有必要里程碑均已通過驗收。
   5. 沒有未處理的關鍵待確認事項。
   6. 未解決風險及剩餘事項已明確記錄。
2. 未實際取得驗證證據時，不得宣稱計畫已完成。
