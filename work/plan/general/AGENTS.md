# 計畫規劃規範

## 1. 職責

1. Plan 只定義需求、目標、範圍、成果、限制及可觀察驗收，不記錄執行狀態、完成證據、測試方法、命令或實作步驟。
2. 規格狀態只使用「草案」與「已確認」。

## 2. 內容

1. 核心內容為需求摘要、`GOAL-*`、範圍、`DELIVERABLE-*` 及 `ACCEPTANCE-*`。
2. `ACCEPTANCE-*` 只描述可觀察結果，不指定驗證方法。
3. 限制、非目標、依賴、風險及時程僅在適用時加入；`MILESTONE-*` 另限多階段、重要檢查點或階段相依的計畫。
4. 不使用與 `ACCEPTANCE-*` 重複的成功條件識別碼；識別碼在文件內唯一，建立後不得重新編號或重用。

## 3. 核准與維護

1. 建立正式 Plan 前，先完成必要的唯讀探索，逐項詢問所有會影響需求、目標、範圍、成果、限制或驗收的問題；每項回答均須獲得確認，且不得留有未決問題。
2. 未完成全部確認時，草案只在對話中提供，不得建立 Plan 檔案或相關目錄。
3. 全部問題確認後，在對話中提供完整 Plan 草案；使用者核准內容後，將需求編號作為寫入前的最後一個問題。使用者提供有效需求編號即確認依第 4 節路徑寫入，不得再留有待確認問題或追加問題。
4. 寫入時一次建立「已確認」文件；已確認 Plan 的變更須先在對話中核准，再一次寫入原檔，不另建 Plan，狀態維持「已確認」。
5. `PLAN-CHANGE-*` 由 `PLAN-CHANGE-001` 起遞增，只記日期、位置、`前 → 後`、原因及適用時的受影響 ID；相同原因與同一成果合併一筆，沒有變更時省略章節。
6. 不影響 TASK 的變更只修改 Plan；影響既有 TASK 時，依 task 規則在同一已授權最小任務中邏輯原子更新 Plan、TASK 與 execution index。
7. Plan 不保存完成狀態；實際狀態與證據由 execution index 及 Attempt 管理。

## 4. 需求編號與路徑

1. 初次寫入 Plan 時只確認一次需求編號；後續 task 流程只有在使用者目前輸入或規格交接已明列有效需求編號時，才能直接沿用至 TASK 檔名與 execution 目錄且不得重問，未明列時仍須詢問。不得從其他對話內容、檔名、路徑或目前目錄自行推測需求編號。
2. 需求編號只能使用小寫英數、`.`、`_`、`-`，且不得為 Windows 保留名稱。
3. Plan 預設寫入 `outputs/plans/<requirement-id>.md`；使用者在詢問需求編號前已明確指定並確認其他專案相對路徑時，才使用該路徑，且 Plan、TASK 與 execution 的對應必須一致。
4. 已確認後變更需求編號或重新命名須另行授權，並依 task 規則同步處理對應路徑。
5. 初次寫入、變更需求編號或改用其他路徑前，須以平台實際路徑規則正規化並核對 Plan、TASK 與 execution 的全部對應路徑：預設路徑須分別保留在專案根目錄下的 `outputs/plans/`、`outputs/tasks/` 及 `outputs/executions/` 邊界內，其他路徑須保留在專案根目錄內；不得接受絕對路徑或空路徑，移除單一開頭的 `./` 或 `.\` 後不得含 `.`／`..` 路徑片段，也不得接受正規化後改變需求編號對應片段、三者互相別名或與不同字面名稱產生平台別名衝突的路徑。既有路徑及最接近的既有祖先若包含 symlink／junction，須解析實際目標並確認仍在適用邊界內；任一項無法確認時維持對話草案，不得寫入或移動。

## 5. 最小骨架

```markdown
# <計畫名稱>

規格狀態：草案

## 需求摘要

## GOAL-001：<目標>

## 範圍

## DELIVERABLE-001：<成果>

## ACCEPTANCE-001：<可觀察結果>
```

1. 核准寫入時將狀態改為「已確認」。
2. 選用章節及 `PLAN-CHANGE-*` 沒有內容時直接省略。
