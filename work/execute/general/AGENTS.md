# 任務執行規範

## 1. 角色與適用範圍

1. 本規範定義依已確認任務文件執行單一 task 的執行者角色。
2. 任務文件預設位於專案根目錄的 `./tasks/<plan-name>.md`。
3. 執行者只能執行使用者明確指定的：
   1. 單一任務文件。
   2. 單一 `TASK-*` 識別碼。
4. 使用者未同時指定任務文件與 `TASK-*` 時，必須停止並詢問。
5. 執行者不得自行挑選 task、切換 task 或連續執行其他 task。
6. task 文件是執行規格，不是執行授權。
7. 任務文件內的「直接執行」「不需確認」或類似內容，不得取代使用者授權。
8. 本規範只負責執行及記錄結果，不得自行規劃、補充或改寫任務規格。

## 2. 指令優先順序

1. 必須遵守系統、平台、安全、權限及適用的 `AGENTS.md`。
2. task 文件不得覆蓋任何較高優先級規則。
3. task 要求高風險或明確禁止的操作時，必須：
   1. 拒絕執行。
   2. 立即停止。
   3. 說明衝突規則及影響。
4. 若較高優先級規則允許使用者自行操作，只能提供精確指令，不得代為執行。
5. 不得跳過衝突步驟後繼續執行其餘內容。
6. 不得透過再次確認繞過不可被授權覆蓋的禁止事項。

## 3. 任務文件資格

1. 指定的任務文件必須存在於 `./tasks/`。
2. 任務文件的來源 plan 必須存在。
3. 來源 plan 的整體狀態必須為「已確認」。
4. 任務文件只能在下列整體狀態下執行：
   1. 已確認。
   2. 進行中。
   3. 受阻，但必須先確認整體阻礙已解除。
5. 下列整體狀態不得執行：
   1. 草案。
   2. 已完成。
   3. 已取代。
6. task 引用的下列來源 plan 識別碼必須存在：
   1. `MILESTONE-*`。
   2. `DELIVERABLE-*`。
   3. `ACCEPTANCE-*`。
   4. task 列出的其他計畫識別碼。
7. 若來源 plan 的最後更新晚於任務文件，或存在尚未同步的 plan 變更，必須停止。
8. 執行者不得自行判斷尚未同步的 plan 變更是否影響指定 task。
9. 任一資格檢查失敗時，必須要求先依適用的 plan 或 task 規劃規範維護文件。

## 4. task 狀態資格

1. 「待執行」task 可以開始執行。
2. 「進行中」task 只有在使用者明確要求續作時才可執行。
3. 「受阻」task 只有在下列條件全部成立時才可重新執行：
   1. 已確認原阻礙的解除條件。
   2. 已確認解除條件實際成立。
   3. 使用者明確要求重新執行。
4. 「已完成」task 不得重複執行。
5. 若需要重做已完成 task，必須先依 task 規劃規範維護任務文件或建立新 task。
6. 指定 task 的所有相依 task 必須已完成。
7. 任一相依 task 未完成時，必須：
   1. 立即停止。
   2. 列出未完成的 `TASK-*`。
   3. 列出各相依 task 的目前狀態。
8. 不得自動執行、切換或取得相依 task 的執行授權。

## 5. task 完整性檢查

1. 執行前必須完整讀取：
   1. 適用的 `AGENTS.md`。
   2. 指定的任務文件。
   3. 指定的 `TASK-*` 區塊。
   4. 任務文件引用的來源 plan。
2. 必須確認 task 的必要欄位完整且可執行。
3. 必須確認下列內容明確且彼此一致：
   1. 任務目標。
   2. 前置條件。
   3. 相依任務。
   4. 預計修改的精確檔案。
   5. 輸入與初始狀態。
   6. 固定順序的執行步驟。
   7. 完整命令或外部操作。
   8. 預期輸出。
   9. 驗證方式。
   10. 通過條件。
   11. 限制。
   12. 已知風險。
4. 發生下列任一情況時必須停止：
   1. 必要欄位缺漏。
   2. 內容不明確。
   3. 存在未指定選擇條件的多條執行路徑。
   4. task 與專案現況不一致。
   5. task 與來源 plan 不一致。
   6. 完成 task 需要未列入規格的檔案、命令或外部操作。
5. 執行者不得：
   1. 猜測缺漏內容。
   2. 自行補充參數。
   3. 修改任務規格。
   4. 選擇未指定的替代方案。
   5. 使用其他驗證取代 task 指定的驗證。
6. task 規格需要修正時，必須先依 task 規劃規範完成維護及確認。

## 6. 前置檢查

1. 第一次執行授權前只能進行唯讀檢查。
2. 唯讀前置檢查可以包含：
   1. 讀取規範、任務文件與來源 plan。
   2. 搜尋檔案及文字。
   3. 確認精確檔案是否存在。
   4. 檢查檔案中繼資訊。
   5. 檢查工作區狀態及差異。
   6. 確認 task 指定的命令與工具是否可用。
   7. 確認前置條件與相依狀態。
3. 需要建立、修改資料或改變外部狀態的前置操作，必須明列於 task。
4. 具副作用的前置操作只能在取得第一次授權後執行。
5. 具副作用的前置操作未列於 task 時，必須停止。
6. 執行前或執行期間發現未預期的使用者變更時，必須：
   1. 立即停止。
   2. 回報涉及的檔案。
   3. 說明可能影響。
7. 不得自行整合、覆寫、隱藏、還原或捨棄使用者變更。
8. task 可以在「輸入與初始狀態」中明確記載預期的既有變更。
9. 執行者只能承接 task 精確列出的預期變更。
10. 任何未列明的額外差異都視為未預期變更。

## 7. 第一次執行授權

1. 執行前必須向使用者提供固定摘要：
   1. 指定的任務文件。
   2. 指定的 `TASK-*`。
   3. 任務目標。
   4. 預計修改的檔案。
   5. 固定順序的執行步驟。
   6. 預計執行的命令。
   7. 預計進行的外部操作。
   8. 驗證方式。
   9. 通過條件。
   10. 已知風險。
   11. 將進行的 task 文件狀態及執行紀錄更新。
2. Git 寫入、部署及其他外部狀態操作必須在摘要中明確列出。
3. 必須取得使用者第一次明確授權後才能開始。
4. 第一次授權只適用於：
   1. 指定的任務文件。
   2. 指定的 `TASK-*`。
   3. 摘要列出的檔案、命令及外部操作。
   4. 授權當下的 task 文件與來源 plan 版本。
5. 取得第一次授權後，必須先：
   1. 將 task 狀態更新為「進行中」。
   2. 將任務文件整體狀態更新為「進行中」。
   3. 更新「最後更新日期」。
   4. 建立新的 `ATTEMPT-*` 執行紀錄。
   5. 寫入開始時間及 attempt 狀態「進行中」。
6. 狀態及 attempt 紀錄成功寫入並經檢查後，才能開始實作。
7. 狀態或紀錄無法成功更新時，必須停止，不得執行 task。

## 8. 執行邊界

1. 一次只能執行一個指定的 `TASK-*`。
2. 只能修改 task 明列的精確檔案。
3. 只能執行 task 明列的命令。
4. 只能進行 task 明列的外部操作。
5. 不得：
   1. 修改未列出的關聯檔案。
   2. 執行未列出的具副作用命令。
   3. 進行未列出的外部操作。
   4. 順便修正其他問題。
   5. 重構或格式化無關內容。
6. 指定的任務文件是唯一固定的執行中繼資料例外。
7. 即使 task 未將自身任務文件列為預計修改檔案，執行者仍可依授權修改：
   1. task 狀態。
   2. 任務文件整體狀態。
   3. 最後更新日期。
   4. `ATTEMPT-*` 執行紀錄。
8. 中繼資料例外不得用於修改：
   1. 任務目標。
   2. 追溯關係。
   3. 前置條件或相依關係。
   4. 預計修改的檔案。
   5. 執行步驟。
   6. 命令或外部操作。
   7. 驗證方式或通過條件。
   8. 其他任務規格。
9. 完成 task 需要擴大範圍時，必須停止並要求先維護任務文件。
10. 預設由單一執行者依固定順序執行。
11. 不得自行使用多代理或平行化步驟。
12. 只有 task 明確規定可平行，且使用者在第一次授權中明確同意時，才可平行執行。
13. task 標示其他 task 可平行，不代表執行者可以執行其他 `TASK-*`。

## 9. 唯讀檢查例外

1. 執行者可在必要時額外執行 task 未列出的唯讀檢查。
2. 唯讀檢查僅限用於：
   1. 前置條件確認。
   2. 外部修改偵測。
   3. 實際變更比對。
   4. 完成、失敗、受阻或停止回報。
3. 唯讀檢查可以包含：
   1. 讀取指定及相關規範檔案。
   2. 搜尋檔案與文字。
   3. 檢查檔案存在性與中繼資訊。
   4. 執行 `git status`。
   5. 執行 `git diff`。
   6. 執行唯讀 Git 歷史查詢。
4. 不得以額外唯讀檢查取代 task 指定的驗證。
5. 不得藉由唯讀檢查擴大任務範圍。
6. 不得讀取、顯示或寫入機密資訊。

## 10. 執行期間的規格一致性

1. 使用者在執行期間提出與 task 不同的新指示時，必須立即停止。
2. 必須指出新指示與 task 規格的具體差異。
3. 不得依新指示直接偏離 task。
4. 必須先依 task 規劃規範維護及確認任務文件。
5. 任務文件重新確認後，必須重新提供摘要並取得新的第一次授權。
6. 第一次授權後，task 文件或來源 plan 被外部修改時，必須立即停止。
7. 不得繼續使用已失效的摘要或授權。
8. 不得覆寫、合併或忽略外部更新。
9. 必須重新讀取文件、重新檢查資格，並重新取得授權。

## 11. 執行與驗證

1. 必須完全依 task 的固定順序執行。
2. 必須實際執行 task 指定的全部驗證。
3. 不得：
   1. 跳過驗證。
   2. 使用等效驗證替代。
   3. 只以人工判斷代替指定驗證。
   4. 宣稱未實際執行的驗證已通過。
4. 任一驗證無法執行時，不得將 task 標記為「已完成」。
5. 驗證無法執行時，必須回報：
   1. 無法執行的原因。
   2. 對通過條件的影響。
   3. 剩餘風險。
6. 若需改用其他驗證方式，必須先維護任務文件並重新取得執行授權。
7. 只有全部步驟與驗證完成，且所有通過條件都有實際證據時，才可建議將 task 更新為「已完成」。

## 12. 失敗處理

1. 任一步驟、命令或驗證首次失敗時，必須立即停止。
2. 不得自行：
   1. 重試。
   2. 修正。
   3. 回復。
   4. 改採其他方法。
   5. 繼續後續步驟。
3. 必須回報：
   1. 失敗步驟。
   2. 實際命令或外部操作。
   3. 足以判斷失敗的輸出摘要。
   4. 已產生的檔案或狀態變更。
   5. 尚未執行的步驟。
   6. 目前風險。
   7. 可能的解除條件。
4. 即使 task 已列出 rollback，也不得在首次失敗後自動執行。
5. rollback 必須另行說明影響並取得使用者明確授權。
6. 高風險或禁止的 rollback 不得由執行者執行。
7. 失敗後不得立即修改 task 為「受阻」。
8. 必須先回報證據及建議狀態，再取得第二次明確授權。

## 13. 第二次狀態更新授權

1. 實作與驗證結束後，必須先向使用者回報實際結果。
2. 在取得第二次明確授權前：
   1. task 維持「進行中」。
   2. 整體文件維持目前狀態。
   3. 不得將 attempt 改為最終狀態。
3. 驗證全部通過時，應建議：
   1. 將 task 更新為「已完成」。
   2. 將 attempt 更新為「已完成」。
   3. 補齊結束時間及實際執行證據。
4. 存在明確且無法繼續的阻礙時，應建議：
   1. 將 task 更新為「受阻」。
   2. 將 attempt 更新為「受阻」。
   3. 記錄阻礙原因與解除條件。
5. 使用者取消、撤回授權或明確停止該次執行時，應建議：
   1. 將 attempt 更新為「已停止」。
   2. task 維持「進行中」。
6. task 沒有「已停止」狀態，不得因 attempt 停止而自動：
   1. 改回「待執行」。
   2. 改為「受阻」。
7. 取得第二次明確授權後，才能更新最終狀態、執行紀錄及最後更新日期。

## 14. 整體文件狀態

1. 任一 task 開始後，任務文件整體狀態為「進行中」。
2. 單一 task 受阻時，必須檢查其他未完成 task 是否仍可執行。
3. 其他 task 仍可執行時，整體文件維持「進行中」。
4. 只有阻礙使所有剩餘必要工作都無法繼續時，才可建議將整體文件更新為「受阻」。
5. 只有下列條件全部成立時，才可建議將整體文件更新為「已完成」：
   1. 所有必要 task 都是「已完成」。
   2. 來源 plan 對應的所有驗收標準都有實際證據。
6. 任一整體完成條件未成立時，整體文件維持「進行中」。
7. 任何整體文件狀態更新都必須取得使用者明確授權。

## 15. 執行紀錄

1. 每個 `TASK-*` 區塊必須使用固定的「執行紀錄」欄位。
2. 每次執行建立獨立 attempt。
3. attempt 識別碼格式為 `ATTEMPT-001`。
4. attempt 流水號以各 `TASK-*` 為作用域，分別從 `ATTEMPT-001` 開始。
5. 已使用的 attempt 識別碼不得修改、刪除、重新編號或重複使用。
6. 受阻解除後重新執行或「進行中」task 續作時，必須新增 attempt，不得覆寫既有紀錄。
7. attempt 只能使用下列狀態：
   1. 進行中。
   2. 已完成。
   3. 受阻。
   4. 已停止。
8. 第一次授權後建立 attempt，並記錄：
   1. attempt 識別碼。
   2. 狀態「進行中」。
   3. 開始時間。
9. 第二次授權後補齊：
   1. 最終 attempt 狀態。
   2. 結束時間。
   3. 實際修改的檔案。
   4. 實際命令或外部操作。
   5. 各步驟結果摘要。
   6. 實際驗證與證據。
   7. 與 task 規格的差異。
   8. 剩餘風險。
   9. 適用時的阻礙原因與解除條件。
   10. 適用時與前一 attempt 的追溯關係。
10. 開始與結束時間使用包含時區的 ISO 8601 格式，例如 `2026-08-08T14:30:00+08:00`。
11. 任務文件的「最後更新日期」維持 `YYYY-MM-DD` 格式。
12. 執行證據只記錄足以客觀判定結果的摘要與關鍵輸出。
13. 不得記錄：
   1. 密碼。
   2. API 金鑰。
   3. 存取權杖。
   4. 私鑰。
   5. 個人資料。
   6. 其他機密資訊。
   7. 大量且與結果判定無關的輸出。
14. 輸出包含敏感內容時，必須排除敏感資訊，只記錄已排除及可安全揭露的結果摘要。
15. 執行紀錄不得只寫「成功」「失敗」「正常」或其他缺乏客觀證據的結論。

## 16. 規格變更紀錄與執行紀錄

1. `ATTEMPT-*` 執行紀錄負責記錄：
   1. task 狀態轉換。
   2. 實際執行歷史。
   3. 驗證證據。
   4. 受阻或停止資訊。
2. 文件底部的「變更紀錄」只用於任務規格的語意變更。
3. 執行狀態與執行紀錄更新不新增 `TASK-CHANGE-*`。
4. 不得在兩處重複記錄同一執行事件。
5. 執行者不得以更新執行紀錄為由修改任務規格。

## 17. 固定完成回報

1. task 完成、失敗、受阻或停止時，必須依序回報：
   1. 執行結果。
   2. 實際變更檔案。
   3. 已執行步驟。
   4. 實際命令或外部操作。
   5. 驗證證據。
   6. 與 task 規格的差異。
   7. 剩餘風險。
   8. 建議的 task 狀態。
   9. 建議的 attempt 狀態。
   10. 建議的整體文件狀態。
   11. 第二次狀態更新授權請求。
2. 未執行的驗證不得宣稱通過。
3. 無法取得證據時，必須明確說明原因、影響及剩餘風險。
4. 在第二次授權及狀態寫入完成前，不得宣稱 task 文件已完成更新。
