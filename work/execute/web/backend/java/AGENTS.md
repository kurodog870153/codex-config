# Java 後端任務執行規範

## 1. 適用方式

1. 本規範用於執行已確認任務文件中的 Spring Boot 後端核心開發 task。
2. 使用本規範時，execute hierarchy 必須依序包含：
   1. `general`
   2. `web/backend`
   3. `web/backend/java`
3. 本規範只補充 Java 與 Spring Boot 特有的執行要求。
4. 未涵蓋事項依 `general` 與 `backend` execute 處理。
5. 若相同層級的規則衝突，以後載入且更具體的本規範為準。
6. 系統、平台、安全、權限及其他更高優先級規則不受前項影響。
7. 執行者只負責依指定 task 執行及記錄結果，不得規劃、補充或改寫任務規格。

## 2. 適用範圍與技術基線

1. 本規範只適用於 Spring Boot 後端專案。
2. Java、Spring Boot、建置工具及相依套件版本必須以指定 task 與目標專案現況為準。
3. 執行前必須確認 task 已精確指定適用的：
   1. Java 與 Spring Boot 版本。
   2. Maven、Gradle 或其他既有建置工具及 wrapper。
   3. 必要的 Spring 模組與相依套件。
   4. 模組、source set、套件與檔案位置。
   5. 完整建置、測試、格式檢查及靜態分析命令。
4. 專案提供 Maven Wrapper 或 Gradle Wrapper 時，必須使用 wrapper。
5. 不得自行升級版本、替換建置工具、引入新框架、加入相依套件或改變技術基線。
6. task 未精確指定必要版本、工具、依賴、檔案或命令時，必須停止。
7. 部署、發布、基礎設施、執行環境佈建、監控及日常維運不屬於本規範範圍。

## 3. Java 後端前置檢查

1. 除 `general` 與 `backend` execute 的前置檢查外，執行前必須唯讀確認：
   1. Java 與 Spring Boot 實際版本符合 task。
   2. 建置工具、wrapper 與 task 指定內容一致。
   3. task 列出的 Spring 模組與依賴已存在或其變更已明確獲得授權。
   4. 預計修改的 Java、設定、migration 與測試檔案位置正確。
   5. 既有分層、模型、交易及錯誤處理方式與 task 一致。
   6. task 指定的命令可由目標專案既有工具執行。
2. 只能以專案既有檔案確認現況，不得依通用 Spring Boot 慣例推測。
3. 現況與 task、來源 plan 或本規範不一致時，必須停止並回報精確差異。
4. 不得為了繼續執行而自行建立相容層、暫時性繞過方式或全面架構改造。

## 4. 固定分層與依賴方向

1. Spring Boot 後端能力必須嚴格採用下列分層：
   1. `Controller`
   2. `Business Service`
   3. `Service`
   4. `Repository`
2. 依賴方向固定為：
   1. `Controller` → `Business Service`
   2. `Business Service` → `Service`
   3. `Service` → `Repository`
3. 禁止跨層呼叫，包括：
   1. `Controller` 直接呼叫 `Service`。
   2. `Controller` 直接呼叫 `Repository`。
   3. `Business Service` 直接呼叫 `Repository`。
4. 禁止下層反向依賴上層。
5. 執行者只能依 task 指定的層級、責任、精確檔案及直接依賴實作。
6. task、來源 plan 或既有架構不符合固定分層時，必須停止；不得只限制新程式碼、保留已知衝突後繼續執行。

## 5. 分層執行責任

1. `Controller` 只能負責：
   1. 對外 API 契約。
   2. Request 與 response 的接收及回傳。
   3. 輸入格式、必填值及基礎約束驗證。
   4. 將請求交由 `Business Service` 處理。
2. `Controller` 不得承擔使用案例編排、業務規則、交易邊界或資料存取。
3. `Business Service` 只能負責：
   1. 使用案例編排。
   2. 跨 `Service` 的業務流程。
   3. 使用案例及跨領域規則驗證。
   4. 交易邊界。
4. `Business Service` 只能透過 `Service` 使用領域與資料能力。
5. `Service` 只能負責：
   1. 單一領域能力。
   2. 領域業務規則、狀態及操作條件驗證。
   3. 封裝對 `Repository` 的資料操作需求。
6. `Service` 不得處理 HTTP request、response、使用案例編排或其他傳輸層責任。
7. `Repository` 只能負責資料存取、持久化查詢、寫入能力及 task 指定的資料完整性要求。
8. `Repository` 不得承擔使用案例編排、業務流程、API 契約或傳輸層驗證。
9. task 未將每項行為、驗證及交易責任配置到唯一層級時，必須停止。

## 6. 資料模型隔離與轉換

1. 下列模型必須完全隔離：
   1. API request 與 response。
   2. 業務模型。
   3. Persistence entity。
2. 任一模型不得直接作為另一類模型使用。
3. 執行模型轉換前，必須確認 task 已指定：
   1. 各模型的責任與精確檔案。
   2. 模型間的轉換方向。
   3. 每個轉換的責任層級與精確檔案。
   4. 欄位、空值、驗證、預設值及相容性行為。
   5. 轉換測試、預期結果及通過條件。
4. 只能使用 task 指定且專案既有的轉換方式。
5. 不得自行引入 mapping 函式庫、程式碼產生工具或未列明的共用模型。
6. 必要模型、轉換責任或驗證缺漏時，必須停止。

## 7. 驗證與交易責任

1. 驗證責任固定為：
   1. `Controller`：輸入格式、必填值及基礎約束。
   2. `Business Service`：使用案例及跨領域流程規則。
   3. `Service`：單一領域規則、狀態及操作條件。
2. 相同規則不得由多個層級重複負責。
3. 交易邊界固定由 `Business Service` 負責。
4. 涉及交易時，必須確認 task 已指定：
   1. 交易開始與結束邊界。
   2. 交易內的固定操作順序。
   3. 成功時的 commit 行為與最終資料狀態。
   4. 失敗時的 rollback 行為與最終資料狀態。
   5. 初始狀態、驗證命令、預期結果及客觀通過條件。
5. 不得在 `Controller`、`Service` 或 `Repository` 建立額外交易邊界。
6. 交易規格或驗證缺漏時，必須停止。

## 8. 統一 API 錯誤契約

1. Spring Boot Web 成果必須嚴格依 task 實作統一且穩定的 API 錯誤契約。
2. 執行前必須確認 task 已明列：
   1. 驗證失敗、業務失敗及系統失敗的分類。
   2. 內部錯誤與 API 回應的固定映射。
   3. HTTP 狀態、對外錯誤識別碼及回應內容。
   4. 不得暴露的堆疊、內部實作、機密或敏感資訊。
   5. 預計修改的例外、錯誤模型及處理器精確檔案。
   6. 每類錯誤的測試案例、預期回應及通過條件。
3. 只能沿用 task 與專案既有錯誤契約，不得自行補足、重新命名或建立不相容格式。
4. 任一必要錯誤契約資訊缺漏時，必須停止。

## 9. Spring Boot 領域執行

1. Web、Validation、Data、Transaction、Security 與 Messaging 只有在 task 明確列為適用時才能執行。
2. Web 執行必須嚴格遵循 task 指定的 API 契約、request、response、狀態碼、錯誤契約、權限及相容性要求。
3. Validation 執行必須依 task 將每項規則配置到固定且唯一的責任層級。
4. Data 執行必須遵循 task 指定的資料所有權、關係、完整性、讀寫行為及模型轉換責任。
5. Transaction 執行必須遵循本規範的固定交易邊界，並驗證 commit 與 rollback 行為。
6. Security 執行必須依 task 驗證合法、未驗證、權限不足及跨資源或跨租戶存取情境。
7. Messaging 執行必須依 task 處理契約、序列化、轉換、重複傳遞、排序、重試、冪等性及失敗行為。
8. task 未定義適用領域的必要行為、檔案或驗證時，必須停止。

## 10. Schema migration 與資料轉換

1. Schema migration 與既有資料轉換只能在 task 明確指定的非正式環境執行。
2. 執行前必須確認 task 已指定：
   1. 精確 migration 或轉換檔案。
   2. 初始 schema 與資料狀態。
   3. 固定執行順序與完整命令。
   4. 預期 schema 與資料結果。
   5. 驗證方式與客觀通過條件。
   6. 失敗停止條件。
   7. 回復方式及其授權要求。
3. 不得對正式環境或正式資料執行操作。
4. 禁止刪除資料、不可逆轉換及其他破壞性資料操作。
5. 首次失敗後不得自動 rollback；任何允許的回復操作仍須另行取得授權。
6. task 未列出必要保護措施或現況與初始狀態不一致時，必須停止。

## 11. 相依套件與設定變更

1. 新增、移除或更新相依套件前，必須確認 task 已指定：
   1. 精確版本與變更原因。
   2. 預計修改的建置或鎖定檔。
   3. 完整命令及外部操作。
   4. 相容性限制及驗證方式。
   5. 已取得的必要授權。
2. Spring Boot 設定變更只能修改 task 明列的精確檔案與設定項目。
3. 不得自行加入 starter、plugin、repository、annotation processor、測試工具或架構驗證工具。
4. 不得讀取、顯示、寫入或傳送真實密碼、API 金鑰、存取權杖、私鑰或其他機密資料。
5. 完成成果需要 task 未列出的依賴、設定或機密資料時，必須停止。

### Lombok 使用規範

1. 專案已配置 Lombok 時，應適度使用明確註解減少樣板程式碼，優先考慮 `@Getter`、`@Setter`、`@RequiredArgsConstructor` 與 `@Builder`。
2. 應避免使用會一次產生多種行為且不易辨識影響範圍的 `@Data`。
3. 禁止使用會隱藏受檢例外或資源生命週期的 `@SneakyThrows` 與 `@Cleanup`。
4. 使用 `@EqualsAndHashCode` 或 `@ToString` 前，必須評估物件語意、關聯欄位、循環參照、延遲載入及敏感資料暴露風險。
5. JPA entity 與序列化模型不得未經評估使用 Lombok 自動產生 `equals`、`hashCode`、`toString` 或建構子；使用 `@Builder` 前亦須確認不會破壞持久化、序列化或反序列化需求。
6. 專案尚未配置 Lombok 時，不得自行新增依賴或 annotation processor；必須先提出新增需求，並確認 task 已明列版本、建置檔、修改內容、命令及驗證方式且取得必要授權。

## 12. 分層測試

1. 必須完整執行 task 指定且適用的：
   1. `Controller` 契約、輸入驗證、錯誤契約及權限測試。
   2. `Business Service` 使用案例、跨領域規則、交易 commit 與 rollback 測試。
   3. `Service` 領域規則、狀態及失敗行為單元測試。
   4. `Repository` 查詢、寫入及資料完整性整合測試。
   5. API、業務與 persistence 模型轉換測試。
   6. 必要的跨層整合測試。
2. 只能使用 task 指定且專案既有的測試框架、fixture、mock、stub、container 與測試資料建立方式。
3. 不得自行新增、刪除、替換或跳過測試。
4. 測試不得連線正式外部服務、使用真實機密資料或依賴不可重現的共享狀態。
5. 適用測試缺漏、無法執行或與 task 預期不一致時，必須停止。

## 13. 架構驗證

1. 每個 task 都必須驗證固定分層、禁止跨層呼叫、禁止反向依賴及模型隔離。
2. task 指定既有自動化架構驗證時，必須使用其精確設定、測試檔案及命令。
3. 專案沒有既有自動化架構驗證時，必須依 task 指定的固定人工程序逐檔檢查：
   1. Java package 與 import。
   2. `Controller` 只依賴 `Business Service`。
   3. `Business Service` 只透過 `Service` 使用領域與資料能力。
   4. `Service` 只透過 `Repository` 存取資料。
   5. `Repository` 未依賴任何上層。
   6. API、業務與 persistence 模型未互相直接取代。
4. 人工檢查必須使用 task 明列的精確檔案、允許與禁止依賴及逐檔通過條件。
5. task 未提供完整人工檢查程序時，必須停止。
6. 不得自行引入 ArchUnit 或其他架構驗證依賴與工具。

## 14. 固定驗證順序

1. Java 後端 task 必須依下列固定順序驗證：
   1. 受影響範圍編譯，或 task 指定的專案既有等效檢查。
   2. 受影響的既有測試。
   3. 本 task 新增或修改的測試。
   4. 適用的格式檢查與靜態分析。
   5. 自動化或固定人工架構驗證。
2. 每項驗證只能使用 task 明列的執行目錄、完整命令或人工步驟、初始狀態、預期輸出及通過條件。
3. 不得改變驗證順序、合併步驟或使用等效命令替代。
4. 任一步驟未取得符合 task 的客觀證據時，不得繼續後續驗證或建議完成 task。

## 15. Java 後端停止條件

1. 發生下列任一情況時，必須立即停止：
   1. task 必要資訊缺漏、不明確或矛盾。
   2. task 與來源 plan、專案現況或適用規範不一致。
   3. 既有架構不符合固定分層或依賴方向。
   4. 模型隔離、轉換、驗證、交易或錯誤責任未明確指定。
   5. 完成成果需要 task 未列出的檔案、依賴、設定、命令或外部操作。
   6. 需要自行選擇 Spring Boot 功能、技術、架構或實作路徑。
   7. 發現未預期的工作區、schema、資料或外部狀態。
   8. 需要處理正式環境、正式資料或破壞性資料操作。
   9. 任一命令、步驟或驗證首次出現非預期失敗。
   10. 需要讀取、顯示、寫入或傳送機密資料。
2. 首次失敗後不得重試、修正、rollback、改用其他命令或繼續後續步驟。
3. 停止後必須依 `general` 與 `backend` execute 回報失敗命令、實際輸出、已完成步驟、目前狀態、剩餘風險及解除條件。

## 16. Java 後端完成條件

1. 只有下列條件全部成立時，才可建議將指定 task 更新為「已完成」：
   1. 所有 Java 與 Spring Boot 實作均在 task 明列範圍內完成。
   2. 實際修改檔案、分層、責任及依賴與 task 一致。
   3. API、業務與 persistence 模型完全隔離，且轉換符合 task。
   4. 驗證、交易及錯誤契約均符合固定責任與 task 規格。
   5. 所有命令及外部操作均依 task 固定順序完成。
   6. 固定驗證順序中的所有適用步驟均通過客觀條件。
   7. 架構驗證已確認固定分層、依賴方向及模型隔離。
   8. 未引入未經確認的版本、依賴、工具、設定或技術基線變更。
   9. 未發生未記錄的規格差異。
   10. 已記錄未驗證項目與剩餘風險。
2. task 狀態、attempt 紀錄及任務文件狀態依 `general` execute 的第二次授權流程更新。
3. 在取得第二次明確授權並完成狀態寫入前，不得宣稱任務文件已完成更新。
